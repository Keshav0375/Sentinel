## Plain English Summary

### What Problem This Solves

Task 7.1 defined *what* to score (rubric, dimensions, prompt). Task 7.2 builds the code that actually *does* the scoring — it calls the judge LLM with the rubric prompt and a trajectory, gets back scores, and turns them into a `TrajectoryScore` Pydantic model. Without this, the eval rubric is just a document; with it, the eval system can actually grade incidents.

### What Was Built (Step by Step)

#### 1. `evaluate_trajectory()` — the main entry point

An `async` function that takes:
- `trajectory`: the full incident timeline dict (what every agent did, every tool called, every result returned)
- `ground_truth`: the scenario's correct answers (right service, severity, root cause, recommended fix)
- `incident_id` / `scenario_id`: for correlation in logs
- `client`: a pre-configured `AsyncOpenAI` client pointed at Groq
- `model`: the judge model name (defaults to `llama-3.1-8b-instant` — fast and cheap, different model family from the analysis agents)

It:
1. Formats the user message using `format_judge_input()` from the rubric module
2. Calls `client.chat.completions.create()` with `temperature=0.0` (deterministic judging)
3. Parses the JSON response into a `TrajectoryScore`
4. Returns the result

**Retry logic**: 4 total attempts with delays of 1s/2s/4s between them. Handles both JSON parse failures and API errors. If all 4 attempts fail, returns a zero-scored `TrajectoryScore` so the eval runner doesn't crash — it logs the error and continues with the next scenario.

#### 2. `_parse_judge_response()` — JSON extraction and validation

The judge LLM sometimes wraps its JSON in markdown code fences (` ```json...``` `). `_strip_code_fences()` uses a regex to extract the JSON body before parsing.

After parsing:
- **Missing dimensions**: If the judge didn't score one of the 6 dimensions, it gets a score of 0 with a "not evaluated" reasoning string. This is logged as a warning.
- **Score clamping**: If the judge returns a score like 99 or -3 (LLMs occasionally hallucinate out-of-range values), it's clamped to [0, 5].
- **total_score**: Calculated as the mean of all 6 dimension scores, then clamped to [0, 5] and rounded to 4 decimal places.

#### 3. `_zero_score()` — failure fallback

Creates a `TrajectoryScore` with all dimensions at 0.0 and `total_score=0.0`. Used when all retry attempts fail, so the eval runner can continue instead of crashing. The failing scenario gets counted as a 0 in the report, making the aggregate score reflect the failure honestly.

### Key Decisions

**Dependency injection for the client**: `client: AsyncOpenAI` is a parameter, not imported as a singleton. Tests can pass a mock client; production passes the real Groq client. No global state.

**`temperature=0.0`**: Eval judging should be deterministic. The same trajectory should always get the same score. Zero temperature eliminates randomness from the judge.

**4 attempts, not 3**: `_RETRY_DELAYS = (1.0, 2.0, 4.0)` gives 3 delays between 4 total calls. CLAUDE.md says "3 attempts, 1s/2s/4s" — the 3 delays map to 3 waits between 4 attempts (initial + 3 retries).

**Zero score on total failure, not exception**: If all retries fail, returning a `TrajectoryScore(total_score=0)` lets the runner log the error and grade the remaining scenarios rather than crashing the entire batch eval. A failed scenario is scored as 0, which is an honest representation — the agent pipeline didn't produce a gradeable trajectory.

**Private helpers for testing**: `_strip_code_fences`, `_parse_judge_response`, and `_zero_score` are module-level functions (not methods or closures) so they can be imported and unit-tested directly without mocking an LLM call.
