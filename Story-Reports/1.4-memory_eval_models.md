## Plain English Summary

### What problem this solves

Sentinel has two subsystems that need their own data vocabulary: the memory system (which stores past incidents so the agent can learn from history) and the evaluation system (which grades how well the agent handled each incident). This task defines the Pydantic models for both.

### What was built, step by step

#### Memory models (`memory.py`)

**`EpisodicRecord`** is a past resolved incident stored for future reference. It captures everything the similarity-search system needs: an ID, which service was affected, severity, the symptoms text (which gets embedded into a 384-dimensional vector), what the root cause turned out to be, how it was resolved, and how long it took (MTTR). The `embedding` field holds the float vector used for cosine-similarity search. `created_at` defaults to now(UTC) so records are timestamped automatically. `raw_timeline` is an optional dict holding the full agent trajectory JSON — useful for eval replays.

**`Runbook`** is an ordered list of remediation steps for a specific failure class on a service. Stored in SQLite's `runbooks` table and loaded by the Triage and Remediation agents. Each runbook is tied to a service name and a failure class (like "bad_deploy" or "db_pool_exhaustion").

**`SemanticRecord`** combines a service's metadata (from `ServiceMetadata`) with its associated runbooks. This is the "everything I know about this service" object that gets loaded once per incident from semantic memory.

**`MemoryQueryResult`** wraps the output of a similarity search: a list of `EpisodicRecord` objects paired with their cosine-similarity scores. Results come back in descending score order so the most relevant past incidents appear first.

#### Eval models (`eval_result.py`)

**`EvalDimension`** is a StrEnum with the six grading axes: triage accuracy, root cause correctness, tool efficiency, MTTR (time-to-resolution), remediation safety (did it use the HITL gate?), and communications quality. These map directly to the eval rubric the LLM-as-judge will use.

**`DimensionScore`** is a single score on one dimension: which dimension, a float between 0 and 5, and the judge's reasoning. The `field_validator` rejects anything outside [0, 5] at construction time.

**`TrajectoryScore`** is the full eval output for one incident run: which incident, which scenario, the list of per-dimension scores, an overall score (mean of dimensions, also validated 0-5), and which model acted as the judge. Defaults allow constructing a "blank" score with no dimensions yet graded (useful for error cases where the pipeline failed before producing results).

### Key decisions and trade-offs

**`raw_timeline: dict[str, Any] | None`** — The episodic record optionally stores the complete agent trajectory. This is useful for eval replays and debugging, but it's nullable because records imported from external systems (or legacy data) won't have it.

**`field_validator` for score ranges** — Rather than silently clamping scores, the validators raise `ValidationError` immediately. A score outside [0, 5] indicates a bug in the judge prompt or parsing logic — fail-fast is better than silently accepting invalid data.

**`judge_model` as required field** — Every eval result records which model produced it. This is essential for reproducibility: if scores change between runs, you need to know whether it was the agent that improved or the judge that shifted.

**`= []` for list defaults** — Same pattern as all prior models: pydantic v2 deep-copies mutable defaults per instance, and this avoids the pyright `list[Unknown]` issue that `Field(default_factory=list)` causes.
