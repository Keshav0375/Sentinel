## Plain English Summary

### What problem this solves

The raw scenario JSON files are useful data, but the rest of the system needs typed Python objects. Every tool that reads a scenario — the log generator, the deploy generator, the eval runner — would otherwise have to parse JSON dicts manually and do its own field extraction. This task puts a typed layer between the JSON files and the Python code: a set of Pydantic models that parse, validate, and expose scenario data as proper typed attributes.

### What was built, step by step

#### scenarios.py — Six Pydantic models

**`ScenarioAlert`** models the `alert` block inside a scenario file. It reuses the `AlertSource` and `AlertSeverity` enums from `sentinel.models.alert`. This means if a scenario JSON ever has `"source": "splunk"` (not a valid source), Pydantic rejects it at load time — no silent bad data reaches the agent.

**`KnownRootCause`** holds the technical explanation of what caused the incident. Both `deploy_id` and `commit` are nullable (`str | None`) because several failure classes (downstream outage, config regression) don't have an associated code deploy.

**`GroundTruth`** is the eval judge's answer key. Its `severity` field is typed as `Severity` (P1-P4 enum from `sentinel.models.incident`) and `recommended_action` is typed as `RemediationAction` (rollback/hotfix/scale/restart/escalate enum from `sentinel.models.remediation`). This means loading a scenario with `"recommended_action": "unknown_action"` raises a `ValidationError` immediately — the eval judge never receives invalid ground truth.

**`ScenarioLogEntry`** models individual log lines. The field is named `ts` (not `timestamp`) to match the compact field name used in the JSON files. It uses `LogLevel` from `sentinel.models.log_entry`, so every `level` field is validated against the known levels (DEBUG/INFO/WARNING/ERROR/CRITICAL) at parse time.

**`ScenarioDeploy`** models deploy records. `commit` is nullable because the `config_regression_01` scenario's config change has no associated commit SHA. `description` defaults to `""` so the field is optional in JSON.

**`Scenario`** is the root model that composes all of the above. It's what `load_scenario` returns and what all downstream generator functions accept as input.

#### alert_gen.py — Three functions

**`load_scenario(scenario_id, scenarios_dir=None) -> Scenario`** finds the JSON file in the scenarios directory and parses it with `Scenario.model_validate_json()`. Using `model_validate_json` (rather than `json.load` + `model_validate`) is a minor efficiency: Pydantic parses the JSON string and validates in a single pass. The `scenarios_dir` parameter defaults to `None` and resolves to `data/scenarios/` relative to the package root (4 levels up from the source file). Tests always pass the actual path explicitly — no hidden coupling to the working directory.

**`generate_alert(scenario: Scenario) -> AlertPayload`** creates a fresh `AlertPayload` from a loaded scenario. The alert_id is a new UUID4 on every call, and the timestamp defaults to `now(UTC)`. This means running the same scenario twice produces two distinct alerts — important for the webhook receiver's deduplication logic (which keys on `alert_id`). The `metadata` dict carries `scenario_id` and `failure_class` so the orchestrator can see which synthetic scenario is being run.

**`list_scenarios(scenarios_dir=None) -> list[str]`** scans the directory for `*.json` files and returns sorted stem names (filenames without extension). Returns an empty list if the directory doesn't exist — safe to call even before the data directory is populated.

### Key decisions and trade-offs

**Reusing existing enums rather than defining new ones** — `ScenarioAlert.source` is `AlertSource`, not a new `ScenarioAlertSource`. This creates a direct type-level contract: if the scenario JSON says `"source": "datadog"`, the resulting Python object has `alert.source is AlertSource.DATADOG`. This matters for `generate_alert`, which passes `scenario.alert.source` directly into `AlertPayload` without any conversion.

**`ts` vs `timestamp` field naming** — `ScenarioLogEntry` and `ScenarioDeploy` use `ts` to match the compact JSON. An alternative would have been a Pydantic alias (`Field(alias="ts")`), but that complicates construction and serialization. Instead, the log_gen and deploy_gen modules (task 2.5) will explicitly map `entry.ts → LogEntry.timestamp` when converting between the two representations. The field name difference makes the conversion point explicit rather than hidden.

**`scenarios_dir` parameter injection** — All three functions accept an optional `scenarios_dir: Path | None = None`. This was the key design choice for testability: tests can point directly at `data/scenarios/` in the repo, while production code uses the computed default. Without this parameter, tests would need to set working directory or monkeypatch the module-level constant — both are fragile.
