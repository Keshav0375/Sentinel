## Plain English Summary

### What Problem This Solves

Sentinel runs an agent pipeline that takes 6-10 steps to resolve an incident — triage, log analysis, deploy correlation, remediation drafting, human approval, and Slack comms. Saying "the agent worked" isn't enough. You need to *grade* it: did it identify the right service? Did it find the root cause? Did it gate the rollback behind human approval? Did it write a useful Slack summary?

Task 7.1 builds the **scoring rubric** — the criteria document and prompt that an LLM judge uses to evaluate an incident trajectory. Without this, the judge doesn't know what "a 5" or "a 2" means for any dimension.

### What Was Built (Step by Step)

#### 1. `DimensionRubric` dataclass

A frozen (immutable) dataclass with three fields:
- `dimension`: which of the 6 eval dimensions this rubric describes
- `description`: one sentence explaining what the dimension measures
- `levels`: a `dict[int, str]` mapping each score 0-5 to a concrete definition of what earns that score

Frozen so rubric definitions can't be accidentally mutated at runtime.

#### 2. `DIMENSION_RUBRICS` dict

A `dict[EvalDimension, DimensionRubric]` with entries for all 6 dimensions:

| Dimension | What it grades |
|---|---|
| `triage_accuracy` | Did the agent identify the right service + severity? |
| `root_cause_correctness` | Does the hypothesis match the known root cause? |
| `tool_efficiency` | Right tools in the right order, no redundant calls? |
| `mttr` | How fast was the path to remediation? |
| `remediation_safety` | HITL gate used? Fix matches recommended action? |
| `comms_quality` | Slack summary complete and correct? |

Each dimension has six concrete level definitions. For example, `remediation_safety` level 5 explicitly requires: HITL gate used AND the proposed fix matches the ground-truth recommended action. Level 0 means "proposed a dangerous action without approval."

#### 3. `JUDGE_SYSTEM_PROMPT`

A string constant built programmatically from `DIMENSION_RUBRICS` via `_build_judge_system_prompt()`. Building it from the rubric data (instead of writing it by hand) ensures the prompt and the Python rubric definitions can never drift apart.

The prompt tells the judge LLM:
- Its role (autonomous AI systems evaluator)
- What inputs it will receive (trajectory JSON + ground truth JSON)
- The full rubric for all 6 dimensions (rendered from `DIMENSION_RUBRICS`)
- The exact JSON output format it must return (`{"dimension_scores": [...]}`)
- Strict rules: integers 0-5 only, one-sentence reasoning, no text outside the JSON

#### 4. `format_judge_input(trajectory, ground_truth)`

A helper function that takes:
- `trajectory`: the full incident timeline dict (everything the agent did)
- `ground_truth`: the scenario's known correct answers (severity, affected service, root cause, recommended action)

And returns a formatted user message with both blocks as pretty-printed JSON fenced code blocks, ready to send to the judge LLM. It uses `default=str` in `json.dumps` so non-serializable values like `datetime` objects don't crash the formatting.

### Key Decisions

**Build prompt from rubric data, not separately**: The rubric definitions live once in `DIMENSION_RUBRICS`. `_build_judge_system_prompt()` renders them into the prompt at module load time. If you change a rubric level, the prompt automatically reflects it — no possibility of the prompt and the Python code disagreeing about what a "4" means.

**Frozen dataclass over dict**: `DimensionRubric` is a `@dataclass(frozen=True)` rather than a plain dict so typos in field names are caught at import time and mutation of rubric definitions is blocked.

**`format_judge_input` as a separate function**: The judge call (LLM API call, parsing) belongs in `judge.py`. The rubric's only job is defining *what* to ask — how to format the input is part of that and belongs here.
