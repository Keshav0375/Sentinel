## Plain English Summary

### The Problem

We now have six specialist agents, an orchestrator, two database-backed memory systems, a local embedding model, three API routers, and a deduplication cache — all built independently and tested in isolation. But nothing wires them together. When a user runs the server, none of these pieces know about each other.

The `main.py` entrypoint is where all those puzzle pieces click into place. It's the assembly line that runs exactly once at startup: builds each component in the right order, injects each one into the components that need it, and leaves a fully-wired HTTP server ready to serve traffic.

### What Was Built

**`lifespan()`** is a FastAPI async context manager that runs all startup logic before the server starts accepting requests, and teardown logic after it stops. The startup sequence has eight steps in order:

1. **Load config and logging** — read all settings from environment variables (GROQ_API_KEY, DB path, model names, etc.) and configure structured JSON logging.

2. **Create database tables** — call `create_tables()` (idempotent DDL — safe to run every time). Parent directories are created if missing.

3. **Seed data** — run `data.seed` to insert the 8 services and 19 runbooks into SQLite. Uses `INSERT OR REPLACE` so re-running never causes duplicates. Wrapped in a try/except so the app can still start if the `data` package isn't on the Python path (prints a warning).

4. **Build memory clients** — create the three memory systems:
   - `EmbeddingClient.from_model_name("all-MiniLM-L6-v2")` — loads the local embedding model (may download from HuggingFace on first use)
   - `SemanticMemory(db_path)` — SQLite-backed service map and runbooks
   - `EpisodicMemory(db_path, embedding_client)` — SQLite-backed past incident store
   - `ShortTermMemory()` — in-process dict for live incidents

5. **Create Groq client** — build an `AsyncOpenAI` client pointed at `api.groq.com` with the API key from settings. Call `set_default_openai_client(groq_client)` so the Agents SDK uses Groq for all internal operations (including tracing).

6. **Build specialist agents** — construct all five specialists using their factory functions, injecting the right memory clients and model names from config.

7. **Build orchestrator** — wire all five specialists into the orchestrator.

8. **Mount API routers** — create the deduplicator, wrap the orchestrator in a pipeline callback, and include the three routers on the app (`/webhooks/alert`, `/incidents`, `/health`).

**`make_pipeline_fn()`** is extracted as a separate testable factory. It returns the async callback that the webhook fires for each new alert. The callback:
- Calls `Runner.run(orchestrator, input_text, max_turns=15)` to run the full pipeline
- Updates `ShortTermMemory` with `RESOLVED` on success
- Catches all exceptions — sets status to `ESCALATED` and logs the error, but never lets the exception propagate to the webhook background task handler (which would silently discard it anyway)
- Guards all STM updates with try/except KeyError in case the incident was cleared externally during a long pipeline run

**`create_app()` and `app`** — the factory creates a `FastAPI` instance with metadata and the lifespan handler attached. The module-level `app = create_app()` is the singleton that uvicorn imports.

### Key Decisions

**`make_pipeline_fn` as a testable factory:** If `run_pipeline` were defined inline inside `lifespan()`, it would be untestable without running the full startup sequence (which requires a real GROQ_API_KEY and database). Extracting it as a factory means tests can inject a mock orchestrator and mock `Runner.run`, verifying the behavior (STM updates, exception handling, max_turns passthrough) without any infrastructure.

**`set_default_openai_client(groq_client)`:** The Agents SDK uses a global OpenAI client for some operations (tracing, any non-model-specific API calls). Without setting this, the SDK would try to use a default OpenAI client configured with an `OPENAI_API_KEY` environment variable. Since we're using Groq, we redirect the SDK's default to point at Groq. Each agent's model also has the client injected directly via `OpenAIChatCompletionsModel`, so this is a belt-and-suspenders configuration.

**Scenario-less production mode:** In the MVP, the `fetch_logs` and `list_recent_deploys` tools need a `Scenario` object to return synthetic data. In production mode (the lifespan), no scenario is pre-loaded — these tools would return error messages when called. This is intentional: in a real deployment, these tools would be replaced by actual Datadog/CloudWatch API calls. For now, the agent pipeline can still run (it'll just get empty log/deploy data) and the scenario-based testing still works in the `scripts/run_scenario.py` path (task 6.5).

**Graceful seed failure:** The `data.seed` import is wrapped in a try/except `ImportError`. This means the server can start even if launched from a directory where `data` isn't on the Python path — it just logs a warning and proceeds with an empty service map. In normal dev usage (running from the project root), the seed always runs.

**Lifespan vs. module-level initialization:** All initialization is inside `lifespan()`, not at module level. This means `import sentinel.main` and `sentinel.main.create_app()` are safe to call without any environment variables configured — perfect for testing. The lifespan only runs when the app actually starts serving traffic.
