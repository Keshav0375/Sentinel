## Plain English Summary

### The Problem

After the Log Analyst produces a root cause hypothesis — say "AuthMiddleware fails on a null config key" — the next question is: *which deployment caused this?* If you can identify the exact deploy that introduced the bug, you know exactly what to roll back. Without this step, you'd be guessing at remediation.

The Deploy Correlator Agent answers this question. It's a focused investigator: given a service name and time window, it fetches the recent deployment history, ranks each deploy by how suspicious it is (how close in time to the incident? how many files changed? does the description mention the affected module?), and names the most likely culprit with a confidence score from 0 to 1.

### What Was Built

**`build_deploy_correlator_agent()`** is a factory function in `agents/deploy_correlator.py` that creates the Deploy Correlator Agent. The function:

1. Takes a `Scenario` (the source of synthetic deploy history in the MVP) and a Groq `AsyncOpenAI` client.
2. Creates an `OpenAIChatCompletionsModel` with `llama-3.1-8b-instant` — the same fast model used for Triage. Deploy correlation is a structured ranking task (sort a list by multiple criteria and pick the top one), not a complex reasoning task, so the smaller model is the right choice here.
3. Returns an `Agent` with:
   - Name: `"deploy_correlator_agent"`
   - Instructions: loaded from `prompts/deploy_correlator.txt`
   - Tools: exactly **one** — `list_recent_deploys`
   - `output_type=DeployCorrelation` — forces structured JSON output

**`DeployCorrelation`** was already defined in `models/deploy.py` from Phase 1.3. It has four fields:
- `recent_deploys` — all `Deploy` objects reviewed (for the eval judge to audit)
- `suspect_deploy` — the single most suspicious deploy (or `None` if no match)
- `confidence` — float 0.0–1.0 indicating how certain the agent is
- `evidence` — one or two sentences explaining the suspicion

The `suspect_deploy` field is `Deploy | None` — the `None` case is intentional and important. Scenarios like `downstream_outage_01` (third-party API down) have no culprit deploy at all; the agent must express zero confidence and explain why rather than hallucinating a suspect.

### Key Decisions

**Single tool only:** Unlike the Log Analyst (which has two tools), the Deploy Correlator has exactly one: `list_recent_deploys`. The system prompt already tells the agent the suspicion-ranking criteria (timing, scope, module overlap). The agent doesn't need to look up service metadata separately — the deploy records already include the service name, and any log-based corroboration comes from context the Orchestrator passes in the input, not from a tool call.

**Fast model (`llama-3.1-8b-instant`):** Deploy correlation is more ranking than reasoning. The agent receives a formatted list of deploys and must return the highest-suspicion one. This is closer to a classification task than analysis, making the smaller/faster model appropriate.

**Confidence as a gateway:** The 0.0–1.0 confidence field isn't cosmetic — the Remediation Agent's system prompt gates its rollback decision on this value. If confidence < 0.7, the agent chooses hotfix over rollback; if < 0.3, it escalates. Tests verify `DeployCorrelation` correctly holds confidence values at both extremes (0.0 for no-culprit scenarios, 1.0 for certain matches).

**Nested `Deploy` in JSON roundtrip:** `DeployCorrelation` contains `list[Deploy]` and `Deploy | None`, each with a `datetime` field. The test `test_deploy_correlation_json_roundtrip` verifies that a full correlation result serializes to JSON and deserializes back correctly — including nested objects — confirming the structured output schema will parse cleanly when the LLM produces it.
