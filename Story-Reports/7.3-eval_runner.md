## Plain English Summary

### What Problem This Solves

Tasks 7.1 and 7.2 gave Sentinel a rubric (criteria) and a judge (the grading function). But you still had to manually fire a scenario, save the trajectory, then call the judge by hand. Task 7.3 automates the entire loop: fire all 10 scenarios, capture each trajectory, grade each one, and produce a final report — all with a single command: `python scripts/run_eval.py`.

This is what lets you say in a demo: "I ran the full eval suite, here are the scores across all 10 failure classes."

### What Was Built (Step by Step)

#### 1. `EvalRunResult` dataclass

Wraps the output for a single scenario with four fields:
- `scenario_id`: which scenario was run
- `incident_id`: the specific incident ID generated for this eval run
- `score`: the `TrajectoryScore` from the judge
- `pipeline_error`: error message if the agent pipeline crashed (or None if it succeeded)
- `trajectory_missing`: True if SentinelTracer didn't write the trajectory file (usually means the pipeline crashed before completing)

Having these metadata fields means the report can distinguish "the pipeline crashed" from "the pipeline ran but scored 0."

#### 2. `_auto_approve()` — the batch eval HITL bypass

In the live demo, a human types `approve` in the terminal when the Remediation Agent asks for sign-off. In batch eval, no human is watching. `_auto_approve` is an async function with the same signature as the HITL callback — it always immediately returns `"approve"` so the pipeline runs uninterrupted. It's injected into the remediation agent via dependency injection, not hardcoded.

#### 3. `run_scenario_eval()` — runs one scenario end-to-end

For each scenario, this function:
1. Generates a fresh alert with a unique `incident_id` (`eval-{scenario_id}-{alert_id_prefix}`)
2. Builds a fresh set of all 5 specialist agents with the scenario injected into log/deploy tools (so they return that scenario's synthetic data instead of error messages)
3. Injects `_auto_approve` into the remediation agent
4. Runs the orchestrator pipeline
5. Catches any pipeline error (stores it in `pipeline_error`, sets status to ESCALATED, continues)
6. Reads the trajectory JSON that `SentinelTracer` wrote to disk during the pipeline run
7. Enriches the trajectory with the short-term memory timeline (so the judge has both the trace spans and the structured timeline entries)
8. Calls `evaluate_trajectory()` with the trajectory and the scenario's ground truth
9. Returns `EvalRunResult`

Fresh agents per scenario matter because each scenario injects different log/deploy data — if you reused the same agent set, the log analyst would still return the previous scenario's logs.

#### 4. `run_eval()` — the batch loop

Sets up shared infrastructure once (DB, memory clients, Groq client, SentinelTracer registered once globally), then iterates over all scenario IDs. For each scenario:
- If `load_scenario()` raises `FileNotFoundError` → logs the error, skips, continues
- If `run_scenario_eval()` raises an unexpected exception → logs, skips, continues
- Otherwise appends the `EvalRunResult` to the results list

The tracer is registered once globally (not once per scenario) to avoid duplicate span processing. Each scenario gets its own `incident_id`, so SentinelTracer routes spans to the correct trajectory file.

#### 5. `summary_stats()` and `scores_from_results()` — aggregation helpers

`summary_stats()` computes `avg_total`, `pass_rate` (threshold = 3.0/5.0 = 60%), and `failure_rate` (how many scenarios had pipeline errors). `scores_from_results()` extracts just the `TrajectoryScore` list for use in the eval report generator (task 7.4).

#### 6. `scripts/run_eval.py` — the CLI

Supports:
- `python scripts/run_eval.py` — runs all 10 scenarios
- `python scripts/run_eval.py --scenarios bad_deploy_01 db_pool_01` — subset
- `python scripts/run_eval.py --judge-model llama-3.3-70b-versatile` — override judge

After the batch finishes, it:
1. Prints a text summary table (score bar, pass rate, per-scenario rows with PASS/FAIL)
2. Writes `reports/eval_report.json` (machine-readable, consumed by the eval dashboard at `GET /eval`)
3. Writes `reports/eval_report.md` (human-readable Markdown with dimension averages table)

### Key Decisions

**Fresh agents per scenario, not per batch**: The log analyst and deploy correlator tools are built with a specific `scenario` injected. If you reused agents across scenarios, scenario 2 would fetch scenario 1's logs. Building fresh agents per scenario costs a bit of construction time (~milliseconds) but guarantees correct data isolation.

**`_auto_approve` via DI, not patching**: The approval function is injected into `build_remediation_agent(approval_fn=_auto_approve)`. This is exactly how the API-based approval (from task 6.7) works — the same injection point, just a different implementation. No monkey-patching or skipping the HITL step.

**Trajectory dir = `reports/trajectories/eval/`**: Separate from the smoke test trajectories in `reports/trajectories/` so eval runs don't overwrite or mix with manual test trajectories.

**STM enrichment in trajectory**: The judge gets both the raw span trace (what the Agents SDK recorded) and the structured STM timeline (tool calls and handoffs as `TimelineEntry` objects). More context = better judge scoring.
