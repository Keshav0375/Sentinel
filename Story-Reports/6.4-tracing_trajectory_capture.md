## Plain English Summary

### The Problem

The eval system (Phase 7) needs to grade the full pipeline trajectory — not just the final answer, but every intermediate step: which tools were called in what order, what each tool returned, when control was handed from one agent to another. Without capturing this, the eval system would be grading a black box.

There's also a practical debugging need: when a pipeline produces a wrong answer, you want to replay every tool call and handoff to see where the reasoning went wrong.

The tracing system solves both problems: it intercepts every tool call and agent handoff at the SDK level and writes them into (1) the incident's timeline in ShortTermMemory for live inspection, and (2) a JSON trajectory file on disk for the eval system.

### What Was Built

**The Agents SDK has a built-in tracing system.** When an agent runs, the SDK fires callbacks (`on_trace_start`, `on_span_start`, `on_span_end`, `on_trace_end`) for every operation. Tool calls generate `FunctionSpanData` spans. Agent-to-agent handoffs generate `HandoffSpanData` spans. LLM calls generate `GenerationSpanData` spans.

**`SentinelTracer`** is a `TracingProcessor` subclass that hooks into this system via `add_trace_processor()`. It:

1. **Identifies which incident a span belongs to** by reading `span.trace_metadata["incident_id"]`. This metadata is set when `run_pipeline` wraps `Runner.run` with `with agent_trace("incident_pipeline", metadata={"incident_id": incident_id})`. No separate incident-to-trace mapping dictionary is needed — the SDK propagates trace metadata to every span automatically.

2. **Converts tool call spans to `TimelineEntry` records** — `FunctionSpanData` (a tool was called) produces a timeline entry with the tool name as the action and the first 300 characters of the output as the summary.

3. **Converts handoff spans to `TimelineEntry` records** — `HandoffSpanData` (orchestrator transferred control to a specialist) produces a timeline entry with `"handoff → {agent_name}"` as the action.

4. **Skips `AgentSpanData` and `GenerationSpanData`** from the timeline — these are too granular (every agent activation and every LLM call) and would clutter the timeline. They're still captured in the trajectory JSON for the eval system.

5. **On trace completion, writes a JSON trajectory file** to `reports/trajectories/{incident_id}.json`. The file contains the trace metadata, all span exports in order, and a timestamp. This is what the eval judge reads in Phase 7.

**Helper functions** are all pure functions (no state) extracted at module level for easy unit testing:
- `_extract_incident_id(trace)` — reads incident_id from trace metadata
- `_incident_id_from_span(span)` — reads incident_id from span's inherited trace metadata
- `_span_to_timeline_entry(span)` — converts a span to a `TimelineEntry` (or None)
- `_parse_ended_at(span)` — parses the span timestamp with fallback to now()
- `_save_trajectory(...)` — writes the JSON file, creating parent dirs as needed

### Key Decisions

**`span.trace_metadata` over a separate mapping:** The SDK propagates trace-level metadata to every span via the `trace_metadata` property. This means `_incident_id_from_span(span)` can read the incident_id directly from any span without maintaining a `trace_id → incident_id` dict in the tracer. The implementation is simpler and race-condition-free — no risk of a span arriving before `on_trace_start` has stored the mapping.

**Selective timeline recording:** Only `FunctionSpanData` and `HandoffSpanData` become `TimelineEntry` records. `AgentSpanData` (agent activation) and `GenerationSpanData` (LLM call) are silently skipped for the timeline but written to the trajectory JSON. The eval system needs all of them; the timeline (shown in the dashboard and API) only needs the observable actions.

**`cast(dict[str, object], metadata)`:** The SDK's metadata attribute is typed as `dict[str, Any] | None` at runtime, but pyright strict mode reports unknown types when calling `.get()` on an `Any`-typed dict. Using `cast` tells pyright the exact types without changing runtime behavior.

**Trajectory dir = `None` disables file writing:** If `trajectories_dir=None`, `on_trace_end` skips the file write. This keeps the tracer usable in unit tests (no disk I/O) and in scenarios where you only want STM updates but not trajectory files.

**`test_tracer_multiple_incidents_isolated`:** This is the most important test — it verifies that tool calls from two concurrent pipeline runs (different `trace_id`s) land in the correct STM timelines and don't cross-contaminate. This would catch bugs where the tracer uses a global incident_id variable instead of reading from span metadata.
