## Plain English Summary

### The Problem

Once the Log Analyst and Deploy Correlator have identified *what broke* and *which deploy caused it*, someone needs to decide what to do about it — and then actually do it. But "doing it" might mean rolling back a deploy on a production system serving thousands of users. That's dangerous territory. You can't let an AI just start reverting code in production without a human checking the plan first.

The Remediation Agent is where the pipeline goes from analysis to action. And it's the one agent in the system that absolutely cannot be trusted to operate autonomously. It must always get human approval before doing anything. This is the HITL ("Human In The Loop") gate — the most important safety boundary in the entire system.

### What Was Built

**`build_remediation_agent()`** is a factory function in `agents/remediation.py` that creates the Remediation Agent. The function:

1. Takes a Groq `AsyncOpenAI` client and an optional `approval_fn` callback.
2. Creates an `OpenAIChatCompletionsModel` with `llama-3.3-70b-versatile` — the capable reasoning model. Remediation requires careful evidence evaluation: reading log findings, deploy correlation data, and making a risk-assessed judgment call. This is the most reasoning-intensive decision in the pipeline.
3. Returns an `Agent` with exactly three tools and structured output.

**Three tools, each with a specific role:**

- `draft_rollback_pr` — Takes a deploy ID and justification, produces a PR description. It does *not* open a PR. It just writes the plan.
- `draft_hotfix` — Takes a file path and fix description, produces a diff template and test suggestions. It does *not* commit anything. It just writes the plan.
- `request_human_approval` — The HITL gate. Takes the proposed action, risk level, evidence, and proposer. Blocks until a human types `approve` or `reject`. Returns the decision.

**The key architectural constraint:** There is no "execute rollback" tool. There is no "merge PR" tool. There is no "restart service" tool. The agent can only *draft* things and *request approval*. Even if the LLM wanted to take direct action, the tools don't exist to do it. This is tool-level enforcement, not just prompt-level — a much stronger safety guarantee.

**`RemediationPlan`** is the structured output:
- `action_type` — rollback, hotfix, or escalate
- `deploy_id` — which deploy to roll back (null for hotfix/escalate)
- `diff` — the hotfix diff template (null for rollback/escalate)
- `risk_assessment` — one sentence on the risk of the proposed action
- `justification` — why this action was chosen

**Injectable `approval_fn`:** The HITL tool accepts a callback that replaces the default terminal `input()` prompt. In the MVP, the human types `approve` or `reject` in their terminal. In Phase 2, this swaps to a Slack interactive button or GitHub PR review webhook — no code changes in the agent needed, just inject a different function.

### Key Decisions

**Explicit `list[Tool]` annotation:** Pyright caught a subtle type error — `list[FunctionTool]` is not directly assignable to `list[Tool]` because Python's `list` is invariant (unlike `Sequence` which is covariant). The fix is a one-word annotation change (`tools: list[Tool] = [...]`). This is the kind of bug that would be invisible at runtime but could cause unexpected type errors in downstream code.

**Safety tests as a two-layer contract:** The HITL requirement is enforced at two levels:
1. *Structural* (this file): `test_remediation_agent_hitl_gate_present` verifies `request_human_approval` is in the tool list. Without it, the agent literally cannot call the gate.
2. *Prompt* (from 5.1): `test_remediation_hitl_is_mandatory` verifies the system prompt uses "must" or "non-negotiable." Without it, the LLM might choose not to call the gate even though the tool is available.

Both layers are needed. A tool that exists but isn't required by the prompt could be skipped. A prompt that says "must" but doesn't have the tool available is helpless.

**Forbidden tool test:** `test_remediation_agent_no_direct_execution_tools` checks that a list of hypothetical dangerous tool names (`execute_rollback`, `merge_pr`, `restart_service`, `delete_deployment`) are not present. This is a regression guard — if someone accidentally adds a direct-execute tool in a future refactor, the test catches it immediately.
