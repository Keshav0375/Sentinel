## Plain English Summary

### The Problem

Before this task, every agent builder had the Groq provider burned into its signature:
```python
def build_triage_agent(..., groq_client: AsyncOpenAI, model_name: str = "llama-3.1-8b-instant")
```

The `groq_client` was a concrete `AsyncOpenAI` object pointed at Groq's base URL, and
the `model_name` was a bare Groq model name with no provider prefix. Swapping to Anthropic
or Azure would require changing all 6 builder signatures — not just config.

### What Changed

**All 6 agent builders** now have a uniform provider-agnostic signature:
```python
def build_triage_agent(..., *, model_string: str, settings: Settings)
```

Inside each builder:
1. `llm = resolve_model(model_string, settings)` — reads the provider prefix, grabs
   the API key from settings, returns a `LitellmModel` ready for the Agent.
2. `caps = get_capabilities(model_string)` — reads the provider's feature flags.
3. `kwargs["output_type"] = SomeModel` is set **only if** `caps.supports_structured_outputs`
   is True. For Groq (True) and OpenAI (True), output is typed. For Anthropic (False),
   the agent returns plain text and the caller uses `coerce_output` as a fallback.

This means you can now route the triage agent to Anthropic by setting:
```
SENTINEL_TRIAGE_MODEL=anthropic/claude-haiku-4-5
ANTHROPIC_API_KEY=sk-ant-...
```
No code changes. The builder reads the provider from the model string, resolves the key,
and disables structured outputs because Anthropic doesn't support them.

**`main.py`, `run_scenario.py`, `eval/runner.py`** all had duplicate SDK init boilerplate:
```python
groq_client = AsyncOpenAI(api_key=..., base_url=...)
set_default_openai_client(groq_client)
set_default_openai_api("chat_completions")
set_tracing_disabled(True)
```
This was replaced with a single call: `apply_sdk_defaults(settings)`. The groq_client
construction was removed entirely from the agent-building path. In `eval/runner.py`,
a groq_client is still constructed locally inside `run_scenario_eval`, but only for the
judge — the LLM-as-judge component still uses the AsyncOpenAI client directly (a separate
concern from the agent layer, not in scope for task 9.4).

**Tests** were updated throughout:
- All `groq_client: AsyncOpenAI` fixtures removed; replaced by `fake_settings` from the
  new `tests/test_agents/conftest.py`.
- All `isinstance(agent.model, OpenAIChatCompletionsModel)` assertions changed to
  `isinstance(agent.model, LitellmModel)`.
- Model string assertions changed from `"llama-3.1-8b-instant"` to
  `"groq/llama-3.1-8b-instant"` (full provider/model format).
- `run_scenario_eval` call sites in `test_runner.py` updated to the new `settings=`
  parameter instead of `groq_client=`, `analysis_model=`, `triage_model=`.

### Key Decision: Keep groq_client in eval/runner.py for the judge

The LLM-as-judge component (`evaluate_trajectory`) uses an `AsyncOpenAI` client directly
to call the Groq API. Migrating the judge to LiteLLM is a separate concern (it doesn't
use the Agents SDK at all — it's just a raw API call). To keep 9.4 scoped correctly,
the groq_client construction was kept inside `run_scenario_eval` but only for the judge
call. The agent builders use the provider layer.
