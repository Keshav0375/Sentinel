## Plain English Summary

### What problem it solves

When Sentinel handles a live incident, five different agents work on it in sequence — Triage classifies it, Log Analyst examines logs, Deploy Correlator checks recent deploys, Remediation drafts a fix, and Comms writes the Slack message. Each of these agents needs to know what the previous agent found, and at the end the eval system needs the entire history to score how well the pipeline performed.

Short-term memory is the working notepad that holds all of this in one place while an incident is active. It's fast (just a Python dictionary, no disk or network), lives only as long as the process is running, and gets cleared once the incident is resolved and its trajectory has been handed to the eval system.

### What was built

**`ShortTermMemory`** is a plain Python class wrapping a `dict[str, dict]` — one inner dict per active incident, keyed by the incident's ID string (e.g. `"inc-a1b2c3d4"`).

Each incident's inner dict holds:
- `incident_id` — the key itself, repeated for convenience
- `alert` — the original `AlertPayload` object that triggered everything
- `timeline` — a growing list of `TimelineEntry` objects, one per agent step
- `triage_result`, `log_analysis`, `deploy_correlation`, `remediation_plan`, `slack_summary` — set to `None` initially, filled in by agents as they complete
- `status` — starts at `TRIAGE`, advances through `INVESTIGATING → PENDING_APPROVAL → RESOLVED`

**The six methods:**

1. **`create(incident_id, alert)`** — allocates a fresh record with all result fields `None` and an empty timeline. Calling `create` on an existing ID resets it to a clean state.

2. **`add_timeline_entry(incident_id, entry)`** — appends one `TimelineEntry` to the incident's timeline. Every agent calls this after each tool call or handoff so the eval system can reconstruct exactly what happened and in what order. Raises `KeyError` if the incident hasn't been created yet — callers can't accidentally log to a ghost incident.

3. **`get_timeline(incident_id)`** — returns a copy of the timeline list (not the original). This defensive copy means callers can't accidentally clear or reorder the stored timeline by mutating the returned list.

4. **`get_context(incident_id)`** — returns a shallow copy of the full incident dict. Agents and the eval judge call this to see the complete current state: what the previous agents found, what the status is, the full timeline. Raises `KeyError` for unknown incidents.

5. **`update_context(incident_id, **fields)`** — merges keyword arguments into the incident dict. This is how agents write their results back: `stm.update_context(id, triage_result=result, status=IncidentStatus.INVESTIGATING)`. Also added beyond the spec because without it there was no way for agents to update the result fields — `get_context` returns a copy, so mutating the returned dict wouldn't stick.

6. **`clear(incident_id)`** — removes the incident from memory. No-op if the ID doesn't exist (prevents errors when cleanup runs twice). Called after the trajectory is stored in episodic memory and the eval system has finished scoring.

Two introspection properties (`active_incident_ids`, `active_count`) are included for monitoring and debugging — they let the API layer report how many incidents are currently in flight.

### Key design decisions

- **Sync, not async** — all six methods are synchronous. There's no I/O here, no SQLite, no network. Async would add overhead with no benefit, and sync functions are callable from both sync and async contexts.
- **`_require()` helper** — rather than repeating `if incident_id not in self._incidents: raise KeyError(...)` in every method, a single private `_require()` method centralises the guard. Easier to change the error message in one place.
- **Defensive copy in `get_timeline`** — returns `list(...)` so callers can iterate, filter, or even `clear()` the returned list without corrupting the stored state. The eval system reads the timeline once at the end; it shouldn't accidentally break ongoing incident tracking.
- **`update_context` added beyond spec** — the TODO lists `create`, `add_timeline_entry`, `get_timeline`, `get_context`, and `clear`. `update_context` was added because the ARCHITECTURE.md structure shows agents must write `triage_result`, `log_analysis`, etc. as they complete. Without an update method, agents would have to reach into the internal dict directly, which is worse encapsulation.
- **No MemoryStore protocol** — `ShortTermMemory` doesn't implement `MemoryStore`. That protocol is for `EpisodicMemory` and `SemanticMemory` (persistent, query-able stores). Short-term memory has a completely different lifecycle and interface.

### Test coverage

35 tests covering: initial empty state, `create` (field initialisation, overwrite semantics, multiple concurrent incidents), `add_timeline_entry` (append, ordering, KeyError on missing), `get_timeline` (defensive copy, type checking, accumulation), `get_context` (keys present, KeyError on missing, reflects updates), `update_context` (each result field, multiple fields at once, KeyError guard, unmodified fields preserved), `clear` (removes, no-op on missing, does not affect other incidents, makes get raise), introspection properties, and a full end-to-end lifecycle test that walks a complete incident from alert through resolution and cleanup.
