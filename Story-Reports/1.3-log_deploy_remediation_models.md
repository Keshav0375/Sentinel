## Plain English Summary

### What problem this solves

Sentinel's specialist agents each deal with a different kind of evidence: one reads logs, one looks at deploy history, one proposes fixes and asks for human approval. Each type of evidence needs its own vocabulary — a set of data structures both the agent and the calling code can agree on. This task defines those structures for the log analysis pipeline, the deploy investigation, and the entire remediation + human-approval flow.

### What was built, step by step

#### Log models (`log_entry.py`)

**`LogLevel`** is an enum with the five standard levels: DEBUG, INFO, WARNING, ERROR, CRITICAL. It mirrors what real logging systems emit and what the scenario JSON files contain. When the Log Analyst agent asks "give me the ERROR logs from api-gateway," the filter is a `LogLevel` value, not a raw string.

**`LogEntry`** is a single line from a service's logs: when it happened, how serious it was, which service wrote it, the message text, and an optional distributed trace ID. It matches the log objects inside the scenario JSON files exactly, so the generator can deserialize scenario logs directly into these objects.

**`LogQuery`** is the question you ask the log store: "fetch logs for api-gateway between 02:00 and 03:00Z, only ERROR level, containing the word NullPointer." The Log Analyst agent builds this and passes it to the `fetch_logs` tool.

**`LogAnalysis`** is what the agent writes when it's done: a list of recurring error patterns it spotted, a plain-English summary of what's abnormal, the specific log lines that matter most (stack traces, first occurrence, rate-change boundaries), and its hypothesis about the root cause. This is stored in `Incident.log_analysis`.

#### Deploy models (`deploy.py`)

**`Deploy`** is a single deployment event: an ID, the target service, when it happened, who pushed it, the git commit SHA, how many files changed, and an optional description. It maps directly to the deploy objects inside scenario JSON files.

**`DeployCorrelation`** is what the Deploy Correlator agent produces after reviewing recent deploys: the full list of deploys in the time window, the one it suspects most (`suspect_deploy`, or `None` if nothing looks suspicious), a confidence score between 0.0 and 1.0, and a string explaining its reasoning. The `suspect_deploy: Deploy | None` design is intentional — for scenarios like a downstream API outage there may be no suspicious deploy at all, and the agent needs to represent that cleanly.

#### Remediation models (`remediation.py`)

This file encodes the HITL safety contract — the rule that agents can *propose* actions but never *execute* them without human sign-off.

**`RemediationAction`** is the five things an agent can propose: roll back the bad deploy, apply a hotfix patch, scale up resources, restart the service, or escalate to a human.

**`RiskLevel`** (high / medium / low) is attached to every approval request so the reviewer can quickly judge whether to approve immediately or investigate further.

**`RemediationPlan`** is the agent's recommendation: which action, which deploy ID (if rolling back), which code patch (if hotfixing), a risk assessment, and a justification. Both `deploy_id` and `diff` are optional — they're only set for the action types that need them.

**`RollbackPR`** is the draft pull request artifact: title, body, deploy ID, and target branch (defaults to `main`). This object exists to be shown to the human reviewer, not to actually merge the code — in the MVP that last step just prints it. In Phase 2, the orchestrator would call the GitHub API with this data.

**`ApprovalRequest`** is what gets sent to the HITL gate: a plain-English description of the proposed action, its risk level, a summary of the evidence that led to the recommendation, and which agent is proposing it.

**`ApprovalResult`** is the human's response: approved / rejected / timeout, who reviewed it, and an optional comment (used for rejection reasons like "too risky during peak hours"). A validator enforces that `reviewer` is never an empty string — every decision must be attributable to someone (or "cli-input" for the terminal MVP).

### Key decisions and trade-offs

**`suspect_deploy: Deploy | None`** — The Deploy Correlator can't always find a culprit. For scenarios like a downstream outage or a memory leak from an old code path, there's no recent deploy to blame. Making the field explicitly nullable forces every consumer to handle the no-suspect case rather than assuming one always exists.

**`RiskLevel` and `ApprovalStatus` added as StrEnums** — The TODO spec listed `risk_level` as a string field with values "high" / "medium" / "low". Promoting these to enums catches typos at model construction time and makes the HITL gate's display logic simpler (switch on enum value, not string comparison).

**`reviewer` validator** — An empty-string reviewer on an `ApprovalResult` would mean a destructive action was approved with no attribution. The validator catches this at construction time rather than silently allowing it.

**Mutable list defaults as `= []`** — Same decision as task 1.2: pydantic v2 deep-copies list defaults per instance, so `= []` is safe. Using `Field(default_factory=list)` caused pyright strict mode to report an unknown type because the bare `list` callable doesn't carry generic element-type information.
