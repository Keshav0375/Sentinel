## Plain English Summary

### What problem this solves

Sentinel needs realistic incident test cases to drive the agent pipeline and the eval system. Without scenarios, there's nothing to fire at the orchestrator and no ground truth to score the agent against. Each scenario is a complete "incident in a box": an alert that fires, logs to analyze, deploy history to correlate, the actual root cause, and the expected agent response — everything the eval judge needs to grade the agent's work.

### What was built, step by step

#### Scenario schema

The JSON schema from ARCHITECTURE.md §9 was extended with a `ground_truth` block. This addition matters because the eval judge needs a clean, pre-parsed answer key without having to re-interpret `known_root_cause`. The ground truth captures: which severity the agent should assign (P1-P4), which service is affected, a one-line root cause summary, what action the agent should recommend (rollback / scale / etc.), and the guilty deploy ID (or null if no deploy is to blame).

#### bad_deploy_01.json — Null pointer from missing config key

A deploy to `api-gateway` ships a refactored auth middleware that reads a JWT secret from the config service — but the config key `auth.jwt_secret` was never provisioned in production. The service starts up and passes its health check (the config path isn't hit at startup), but every authenticated request immediately throws `NullPointerException in AuthMiddleware.validate()`. The logs include: a startup warning about the missing config key (easy to miss), a flood of NullPointerExceptions with stack traces, cascading 500s, and a red herring log from `notification-service` (which is fine) to test that the agent focuses on the right service. Three deploys are in the window: the culprit (`deploy-abc123` to api-gateway, 15 minutes before the alert) plus an older api-gateway deploy and an innocent user-service deploy.

#### bad_deploy_02.json — Dependency version mismatch

A dependency upgrade deploy to `user-service` bumps `psycopg2` from 2.9.3 to 3.0.0, which removed the `cursor.mogrify()` method used throughout `UserRepository`. Every database call fails immediately with `AttributeError`. The scenario is designed to test two things: first, that the agent correctly identifies the library upgrade (not a feature change) as the culprit; second, that it handles downstream cascade — `auth-service` also starts failing because it depends on user-service for verification, and `api-gateway` opens a circuit breaker. The red herring is a scheduled analytics job that ran normally just before the incident. Three deploys: the culprit (12 files changed, 4 packages upgraded) vs. two older innocent deploys.

#### db_pool_01.json — Connection pool exhaustion

This scenario deliberately has **no suspect deploy** — the payment service's DB connection pool exhausts under a traffic spike (3.8x baseline on a sale day). The root cause is a combination of an unindexed full-table scan in `payment_records.find_pending()` that holds connections for 47+ seconds, combined with the volume spike. The alert fires on p99 latency (8200ms, threshold 500ms) rather than error rate, testing that the agent handles a latency alert correctly. The logs include the autoscaler triggering (correct fix), a red herring from `notification-service` (email queue, unrelated), and a cascade into `order-service`. The deploys list three entries (two old payment-service deploys, one order-service deploy for the promotional pricing engine) — all innocent. The agent must correctly conclude there is no deploy to roll back and recommend scale-up instead.

### Key decisions and trade-offs

**`ground_truth` block added to schema** — ARCHITECTURE.md §9 didn't include this. The `known_root_cause` block describes the technical cause, but the eval judge needs a pre-structured answer key: expected severity, service, action, deploy_id. Parsing that from free-text `known_root_cause.description` would be fragile. The `ground_truth` block is the canonical machine-readable answer key.

**Red herrings in every scenario** — Each scenario includes at least one log line from an unaffected service (notification-service, analytics-pipeline) to ensure the agent doesn't just blame the noisiest service. Real incidents have this noise.

**db_pool_01 deploy_id is null** — The schema explicitly allows `null` for `deploy_id` in both `known_root_cause` and `ground_truth`. This tests the Deploy Correlator agent's ability to return `suspect_deploy: None` with confidence rather than forcing a false attribution.

**14+ log lines per scenario** — The minimum from ARCHITECTURE.md was just 2 example logs. Realistic scenarios need enough signal-to-noise to actually challenge the Log Analyst agent. Each scenario has 14 entries covering: startup, the warning/error onset, the cascade, a red herring, and the alert trigger.
