## Plain English Summary

### The Problem

The webhook receiver (6.1) accepts alerts and starts pipelines. But once a pipeline is running, how do you check on it? Engineers need visibility into what's happening: what incidents are active? What did triage find? Has remediation run yet? Without query endpoints, the system is a black box.

This task adds three read-only endpoints that expose the current state of `ShortTermMemory` — the in-process dict that tracks every active incident.

### What Was Built

**`GET /health`** is the simplest endpoint — a pulse check. It returns three fields:
- `status: "ok"` — always, as long as the service is running
- `version: "0.1.0"` — the application version
- `active_incidents: int` — how many incidents are currently being processed

The health router accepts an optional `ShortTermMemory` — when `None`, it still works but reports zero active incidents. This makes the health check usable before the full DI setup is wired.

**`GET /incidents`** returns a summary list of all currently active incidents held in `ShortTermMemory`. For each incident, it returns four fields:
- `incident_id` — the unique ID (e.g., `inc-a1b2c3d4`)
- `service` — the affected service name (from the original alert)
- `status` — the current pipeline status (`triage`, `investigating`, `remediating`, etc.)
- `alert_severity` — the raw severity from the monitoring system (`critical`, `high`, etc.)

When no incidents are active, it returns `{"incidents": [], "total": 0}` — a 200 response with an empty list, not a 404.

**`GET /incidents/{id}`** returns the full context for a single incident — everything `ShortTermMemory` knows about it:
- The original `AlertPayload` that triggered the incident
- Every `TimelineEntry` logged so far (agent name, action, result summary, timestamp)
- The output of each specialist agent (`triage_result`, `log_analysis`, `deploy_correlation`, `remediation_plan`) — `null` for any agent that hasn't run yet
- The Slack summary if the Comms Agent has run

If the `incident_id` is not found, it returns **404** with a clear error message.

### Key Decisions

**API-layer response DTOs stay in the API modules:** `IncidentListItem`, `IncidentListResponse`, `IncidentDetail`, and `HealthResponse` are defined in their respective API files, not in the `models/` package. The `models/` package contains domain models (AlertPayload, Incident, TimelineEntry) that know nothing about HTTP. The API models are Data Transfer Objects — they exist solely to define the JSON shape of HTTP responses. Mixing them into the domain model package would blur this separation.

**`timeline: list[TimelineEntry]` in `IncidentDetail`:** The response model holds actual `TimelineEntry` Pydantic objects rather than raw dicts. FastAPI serializes them automatically to JSON including datetime fields. This gives the API consumer properly typed, consistently structured timeline data rather than an opaque `list[dict]`.

**`status` as a plain `str` in response models:** Rather than using the `IncidentStatus` enum directly in the response models, both endpoints return `status` as a plain string (via `str(ctx["status"])`). This avoids exposing the internal enum as a fixed contract in the API response — the API can accept additional status values in the future without a schema change. The test verifies the string value is `"triage"` or `"investigating"` rather than the enum object.

**404 on missing incident with `HTTPException`:** FastAPI's `HTTPException` is the idiomatic way to return error responses with a specific status code and detail message. The test `test_get_incident_404_detail_message` verifies the word "not found" appears in the error body, ensuring the message is human-readable rather than a raw Python exception string.

**Same `pyright: ignore[reportUnusedFunction]` pattern:** Inner route functions decorated with `@router.get(...)` trigger pyright's `reportUnusedFunction` in strict mode — same false positive as the webhook receiver. Suppression comments are applied consistently.

**`test_list_and_detail_consistent_ids`** is a cross-endpoint coherence test: it verifies that every `incident_id` returned by the list endpoint can be successfully fetched via the detail endpoint. This catches any bug where STM state and API responses diverge.
