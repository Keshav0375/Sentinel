## Plain English Summary

### What problem it solves

When a new incident arrives, the Triage Agent needs to answer: "Have we seen this before?" If a similar incident happened last week — same service, same symptoms, same root cause — the agent shouldn't have to rediscover everything from scratch. It should recall the past incident's root cause and resolution, and use that to fast-track its diagnosis.

`search_past_incidents` is the tool that gives Sentinel this learning capability. It takes a natural language description of current symptoms (e.g. "connection pool exhausted on payment-service") and finds the most similar past incidents stored in episodic memory using vector embeddings and cosine similarity.

### What was built

**Tool signature:**

```
search_past_incidents(
    symptom_query: str,   # e.g. "connection pool exhausted payment-service"
    top_k: int,           # how many past incidents to retrieve (typically 3-5)
) -> str
```

**How it works step by step:**

1. **Validate inputs** — if `memory` is None, query is empty/whitespace, or `top_k <= 0`, return an error string (tools never raise).

2. **Query episodic memory** — calls `memory.query(symptom_query, top_k=top_k)` which:
   - Embeds the symptom query into a vector using the embedding client
   - Loads all stored incident embeddings from SQLite
   - Computes cosine similarity between the query vector and each stored vector
   - Returns a `MemoryQueryResult` with parallel `records` and `similarity_scores` lists, sorted descending by score

3. **Format results** — `_format_results()` renders each matching past incident as a block showing: incident_id, service, severity, symptoms, root_cause, resolution, MTTR (or "unknown"), and similarity score (3 decimal places). If no matches found, returns "No similar past incidents found."

Example output:
```

  severity:      P1
```

### Key design decisions

- **Uses `memory.query()` not `memory.search_similar()`** — `query()` returns a `MemoryQueryResult` with both records AND similarity scores (parallel lists), while `search_similar()` only returns records. The similarity score is critical context for the Triage Agent — a 0.98 match means "this is almost certainly the same issue", while a 0.3 match means "only vaguely related".

- **Same testability pattern** — logic extracted to `_search_past_incidents()` (callable without ToolContext) and `_format_results()` (pure function on `MemoryQueryResult`). Tests call these directly.

- **Closure-based memory injection** — `make_incident_search_tool(memory)` captures the `EpisodicMemory` instance via closure, keeping `memory` out of the LLM-visible schema. The agent only sees `symptom_query` and `top_k`.

- **MTTR displayed as seconds with fallback** — if `mttr_seconds` is None (incident wasn't properly resolved or timing not captured), shows "unknown" rather than omitting the field. The agent should know when historical MTTR data is missing.

### Test coverage (33 tests)

*Tool wrapping (6):* Returns `FunctionTool`, correct name, non-empty description, schema has `symptom_query` and `top_k`, `memory` not in schema.

*Error handling (6):* None memory → error string (no raise), empty query, whitespace-only query, zero top_k, negative top_k.

*Successful retrieval (13):* Returns string, empty DB → "No similar past incidents found", matching incident appears, top result is most similar (deterministic keyword vectors verify ranking), top_k limits results, result contains Found count, severity, root_cause, resolution, similarity score, mttr, cross-cluster queries (deploy → api-gateway, memory → analytics-pipeline).

*`_format_results` (8):* Empty → "No similar past incidents found", header count, incident_id present, all fields present, similarity score formatted to 3 decimals, mttr "unknown" when None, mttr shown when present, multiple records both shown.
