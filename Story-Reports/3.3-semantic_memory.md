## Plain English Summary

### What problem this solves

The Triage Agent needs to answer questions like "who owns api-gateway?", "what services depend on auth-service?", and "what are the rollback steps for a bad deploy on payment-service?" before it can classify an incident and route it correctly. Without semantic memory, these questions require either hardcoding the answers in the system prompt (fragile, stale) or making external API calls (slow, unreliable). Semantic memory gives the agent a local, fast, pre-loaded knowledge base about the service landscape.

### What was built

**`SemanticMemory`** is a class that loads service and runbook data from the seeded SQLite database and caches the results in memory. It satisfies the `MemoryStore` protocol and provides three domain-specific methods on top of the protocol's four primitives.

**`get_service(name) -> ServiceMetadata`** looks up a service by name and returns its full metadata: team, operational tier (critical/standard/best-effort), oncall channel, GitHub repo URL, description, and the list of services it depends on. If the service doesn't exist in the database, it raises `KeyError` — the caller must handle unknown services explicitly rather than silently getting None.

**`get_dependencies(name) -> list[str]`** delegates to `get_service` and returns just the `dependencies` list. This is a convenience method for the Triage Agent's blast-radius analysis — "if auth-service is down, which services are also affected?"

**`get_runbook(service, failure_class) -> Runbook | None`** looks up the remediation playbook for a specific (service, failure class) pair — for example, ("api-gateway", "bad_deploy") returns the step-by-step rollback instructions. Returns `None` if no runbook exists for that combination, which the agent must handle gracefully. Critically, `None` is also cached — so asking for a missing runbook twice only hits the database once.

**`get_all_runbooks(service) -> list[Runbook]`** loads every runbook for a service across all failure classes. This powers the `query()` protocol method which returns a complete `SemanticRecord` (service metadata + all runbooks). As a side effect, it populates the per-(service, failure_class) cache.

**Cache**: two dictionaries live on the instance — one for services (keyed by name) and one for runbooks (keyed by (service, failure_class) tuple). Both are populated on first access. The caches live for the lifetime of the `SemanticMemory` object — creating a new one per incident means caches never go stale.

**Protocol methods**: `store()` and `delete()` raise `NotImplementedError` with a message pointing at `data/seed.py`. The database is populated at startup, not written to by agents at runtime. The `get()` protocol method delegates to `get_service()` and returns `None` (rather than raising) for unknown names, matching the protocol's contract.

### Key decisions and trade-offs

**`get_service` raises `KeyError`, `get` returns `None`** — There's a deliberate difference. `get_service()` is the domain API used by agents that should know which services exist (if they're asking about an unknown service, something is wrong upstream). `get()` is the protocol primitive that follows the "return None if absent" contract. Two different methods, two different error semantics.

**`None` cached for missing runbooks** — If the agent asks for a runbook that doesn't exist, the result `None` is stored in the cache. Without this, a repeated query for a missing (service, failure_class) pair would hit the database every time. The None-caching means "we looked, there's nothing there" is also remembered.

**Protocol compliance asserted at import time** — The bottom of the module does `assert isinstance(SemanticMemory.__new__(SemanticMemory), MemoryStore)`. This means any future change that breaks protocol conformance (e.g., removing a method, changing a method name) is caught immediately when the module is imported, not silently at the first runtime use. It uses `__new__` to avoid calling `__init__` (which requires a db_path).

**`get_all_runbooks` populates the per-pair cache as a side effect** — When `get_all_runbooks("payment-service")` loads all payment-service runbooks, it stores each one in `_runbook_cache` by (service, failure_class). This means a subsequent `get_runbook("payment-service", "db_pool")` call gets a cache hit even though it was loaded via the "get all" path. The two code paths share the same cache.
