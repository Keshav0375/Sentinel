## Plain English Summary

### What Problem This Solves

Before this task, Sentinel was an agent pipeline that ran silently in the background. You'd fire a scenario via the CLI, watch terminal output scroll by, and eventually see the HITL approval prompt in the terminal. There was no way to observe what was happening without reading raw logs.

Task 6.8 gives Sentinel a **live web dashboard** — a single HTML page you open in a browser that streams the entire pipeline in real time, lets you approve or reject remediation actions with one click, and shows running metrics.

### What Was Built (Step by Step)

#### 1. The Dashboard HTML (`src/sentinel/dashboard/index.html`)

A self-contained HTML file with no external dependencies — pure vanilla HTML, CSS, and JavaScript. It loads in the browser at `http://localhost:8000/`.

**Layout has four zones:**

- **Header bar**: The Sentinel logo on the left, a "Fire Scenario" dropdown on the right populated by fetching `/api/scenarios`. Click ⚡ Fire Scenario and the pipeline starts.

- **Incident info bar**: Appears once a scenario fires. Shows the incident ID (e.g., `inc-3a7f2b1c`), service name, severity badge (color-coded: red=critical, orange=high, blue=warning, green=low), status pill (Running/Resolved), and elapsed time in real time.

- **Agent pipeline cards**: Five cards, one per specialist agent (Triage → Log Analyst → Deploy Correlator → Remediation → Comms). Each card starts gray (idle). When `agent_started` fires, the card gets a blue pulsing border. When `agent_completed` fires, it turns green. Under each card, tool calls appear as sub-items — tool name in purple monospace, with "Running…" replaced by the actual output when `tool_result` arrives.

- **Metrics bar** (footer): Live counters for total tool calls, elapsed time, memory hits (counts `search_past_incidents` calls), and active agent count.

**HITL overlay**: When `hitl_requested` fires (the remediation agent needs human sign-off), a modal dialog slides over the page with an amber warning border. It shows the full approval request text (action, risk level, evidence). Two buttons: ✅ Approve sends `{"action": "approve"}` and immediately continues the pipeline. ❌ Reject shows a text input for an optional rejection reason, then sends `{"action": "reject", "comment": "..."}`.

**Event log**: A scrolling console at the bottom of the pipeline section shows every event received with its timestamp — useful for demo recordings.

#### 2. Scenarios API (`src/sentinel/api/scenarios.py`)

A new `GET /api/scenarios` endpoint that loads all 10 scenario JSON files, runs them through `generate_alert()` (which creates a fresh `alert_id` and timestamp on every call), and returns a list of `ScenarioInfo` objects. The dashboard fetches this on load to populate the dropdown and to know what alert payload to POST when the user fires a scenario.

#### 3. DashboardEventEmitter (`src/sentinel/infra/dashboard_emitter.py`)

The agent pipeline doesn't automatically publish events to the EventBus — only HITL and incident-resolved events were wired before. To make the agent cards light up and tool calls appear, something had to watch the pipeline and emit events.

This is a second `TracingProcessor` (registered alongside `SentinelTracer`) that intercepts Agents SDK spans:

- **`AgentSpanData` span start** → publishes `agent_started` event
- **`AgentSpanData` span end** → publishes `agent_completed` event
- **`FunctionSpanData` span start** → publishes `tool_called` event (with tool name and call ID)
- **`FunctionSpanData` span end** → publishes `tool_result` event (with truncated output)

The emitter keeps a `trace_id → agent_name` map so that tool-call events carry the correct agent name even though `FunctionSpanData` doesn't include "which agent called this tool."

The `_emit()` method schedules the async `bus.publish()` call using `loop.create_task()` — since TracingProcessor callbacks are synchronous but called from within the async pipeline, `asyncio.get_running_loop()` always succeeds and the task runs on the same event loop as the ASGI app.

#### 4. Main.py Updates

Three additions:
- `GET /` route (added in `create_app()`) reads and returns `dashboard/index.html` as an `HTMLResponse`
- `DashboardEventEmitter` created with the shared `EventBus` and registered via `add_trace_processor()`
- `make_scenarios_router()` included so `GET /api/scenarios` is mounted

### Key Decisions

**Single HTML file, no framework**: The task spec required it, and it's the right call for a demo tool. Adding React or Vue would require a build step and add complexity. Vanilla `EventSource` API + `asyncio.TaskGroup`-style promise chaining (via sequential awaits) is sufficient.

**GitHub dark theme**: The dashboard is designed to be recorded. Dark themes look better in screen recordings and suit the DevOps context.

**DashboardEventEmitter as a separate TracingProcessor**: Rather than modifying `SentinelTracer`, which already has 31 tests and a well-defined responsibility, a new processor keeps separation of concerns — SentinelTracer writes to files and STM, DashboardEventEmitter writes to the EventBus.

**Call ID linking**: Tool `tool_called` and `tool_result` events share a `call_id` equal to `span.span_id`. The dashboard uses this to match the "Running…" placeholder with the actual result when it arrives.
