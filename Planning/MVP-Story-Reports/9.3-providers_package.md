## Plain English Summary

### The Problem

After tasks 9.1 and 9.2, Sentinel knows *which* provider to use (from the `groq/model-name` format in config) and validates that the right API key is present — but there's no code yet that actually *does* the routing. When an agent needs to call an LLM, the system still builds a raw Groq client manually and passes it to every agent builder. Tasks 9.3 builds the abstraction layer that bridges config → SDK, so that routing becomes a single function call.

### What Was Built

**`resolver.py` — The routing function.**
`resolve_model("groq/llama-3.1-8b-instant", settings)` does three things:
1. Parses the provider prefix from the model string (`"groq"`)
2. Grabs the right API key from settings (`groq_api_key`)
3. Returns a `LitellmModel` instance ready to pass to `Agent(model=...)`

For Azure specifically, it also writes `AZURE_API_BASE` and `AZURE_API_VERSION` into the process environment, because LiteLLM reads those from env rather than the model constructor.

The function raises `ValueError` for bare model names (no `/`) and for unknown providers, with clear error messages that list what's supported.

**`capabilities.py` — The feature flag table.**
Not every provider supports the same features. OpenAI and Azure support structured JSON outputs and strict schemas. Groq supports structured outputs but not strict schemas (that's what `strict_mode=False` from task 9.1 was for). Anthropic supports neither — it returns plain text.

`get_capabilities("groq/llama-3.3-70b-versatile")` returns a frozen `ProviderCapabilities` object with `supports_structured_outputs=True` and `strict_schemas=False`. Agent builders in task 9.4 will check `caps.supports_structured_outputs` before setting `output_type=` on an Agent, and `caps.strict_schemas` before deciding tool mode.

Unknown providers and bare model names return the safe default (both flags False), so the system degrades gracefully when given something unexpected.

**`output_coercion.py` — The fallback parser.**
When Anthropic (or any provider without structured outputs) returns a response, the agent can't produce a typed Pydantic model directly. `coerce_output(text, MyModel)` handles this:
1. Strips markdown code fences (` ```json ... ``` ` or just ` ``` ... ``` `)
2. Attempts `model_validate_json` on the cleaned text
3. Returns `None` if parsing fails — callers decide how to handle the failure

**`__init__.py` — The clean public API.**
Re-exports all four public names (`resolve_model`, `get_capabilities`, `apply_sdk_defaults`, `coerce_output`) from a single import point. Also houses `apply_sdk_defaults(settings)` — the function that centralizes the two SDK global calls (`set_default_openai_api` + conditional `set_tracing_disabled`). In task 9.4, `main.py`/`run_scenario.py`/`eval/runner.py` will call `apply_sdk_defaults(settings)` instead of duplicating those two lines everywhere.

**`pyproject.toml`** was updated from `openai-agents>=0.0.14` to `openai-agents[litellm]>=0.0.14`. The `litellm` extra was also installed directly via pip for the current dev environment.

### Key Decision: PEP 695 Type Parameters

`coerce_output` is a generic function that takes a Pydantic schema type and returns an instance of that type. Python 3.12 introduced a new syntax for this: `def coerce_output[T: BaseModel](...)`. The old TypeVar approach (`_T = TypeVar("_T", bound=BaseModel)`) would have worked identically at runtime, but ruff (UP047) flags it as deprecated in Python 3.12+ projects. Using the new syntax is cleaner and forward-compatible.
