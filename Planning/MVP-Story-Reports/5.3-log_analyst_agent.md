## Plain English Summary

### The Problem

After triage tells us *which* service is affected and *how urgent* it is, the next question is: *what exactly is wrong?* The raw alert just says "error rate is 34%." To figure out why, you need to look at the actual log lines — the error messages, stack traces, and timestamps that tell the story of what broke and when.

That's the Log Analyst's job. It's the agent that does the detective work: fetching logs, filtering out noise, identifying recurring error patterns, and producing a hypothesis like "AuthMiddleware fails on null config key introduced in the 02:45 deploy."

### What Was Built

**`build_log_analyst_agent()`** is a factory function in `agents/log_analyst.py` that creates a configured Log Analyst Agent. The function:

1. Takes a `SemanticMemory` client (for service dependency context), a `Scenario` (the source of synthetic logs in the MVP), and a pre-configured Groq `AsyncOpenAI` client.
2. Creates an `OpenAIChatCompletionsModel` with `llama-3.3-70b-versatile` — the capable analysis model (equivalent to gpt-4o in reasoning quality). This matters because log analysis requires reading long log dumps and spotting subtle patterns, which a smaller model would miss.
3. Returns an `Agent` with:
   - Name: `"log_analyst_agent"`
   - Instructions: loaded from `prompts/log_analyst.txt` at runtime
   - Tools: exactly two — `fetch_logs` and `get_service_metadata`
   - `output_type=LogAnalysis` — forces the LLM to return structured JSON with error patterns, anomaly summary, key log lines, and a hypothesis

**`LogAnalysis`** was already defined in `models/log_entry.py` from Phase 1.3, so no model changes were needed. The output type has four fields:
- `error_patterns` — list of recurring error message templates (e.g., "NullPointerException in AuthMiddleware.validate()")
- `anomaly_summary` — one paragraph describing when the degradation began
- `key_log_lines` — up to 5 `LogEntry` objects that best evidence the root cause
- `hypothesis` — one sentence root cause hypothesis

### Key Decisions

**Two tools, not one:** The TODO says the primary tool is `fetch_logs`, but the agent also has `get_service_metadata`. This is important for upstream dependency scenarios: if `api-gateway` is failing but the root cause is actually `auth-service` being down, the agent needs to understand the dependency topology. It won't always call `get_service_metadata`, but having it available lets the LLM make that judgment call.

**`llama-3.3-70b-versatile` as the model:** Unlike the Triage Agent (which just classifies and needs speed), the Log Analyst needs to read potentially 20-30 log lines, identify patterns, and reason about causality. The larger model is justified here. The Groq API makes this fast enough for an MVP.

**None scenario at construction time:** The factory accepts `scenario=None` (no crash). If `None` is passed, `fetch_logs` returns an error message when called, which the LLM will include in its analysis. This is by design — failing gracefully at call time rather than at construction time keeps the agent usable even in incomplete pipeline setups.

**No handoffs:** Same as the Triage Agent — the Log Analyst is a specialist. It doesn't route to other agents; it returns its `LogAnalysis` and the Orchestrator decides what happens next.
