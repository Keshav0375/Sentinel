## Plain English Summary

### What problem this solves

The eval system grades the agent across 10 distinct incidents. With only 3 scenarios, all of the same failure class (bad_deploy, db_pool), the eval would give a skewed picture: an agent that's good at one failure type would score well even if it failed completely on others. The remaining 7 scenarios complete the full test matrix: all 5 failure classes, all 8 services, and several adversarial cases designed to distinguish a thorough agent from a shallow one.

### What was built, step by step

#### bad_deploy_03 — Missing environment variable (auth-service)

An OAuth integration deploy ships to production referencing `OAUTH_CLIENT_SECRET` from `os.environ` at request time. The secret was never added to the Kubernetes ConfigMap for production. The service passes its health check (the OAuth code path isn't hit on startup), but every OAuth callback fails with `KeyError`. Notably, password-based login routes continue working fine — only the OAuth routes fail. This tests whether the agent correctly identifies partial service failure rather than treating it as a complete outage.

#### db_pool_02 — Connection leak from unclosed cursors (order-service)

Different from db_pool_01 (a traffic spike). Here, a new batch reconciliation job opens DB cursors in a try block but the `finally` clause only closes the *connection*, not the *cursor*. Leaked cursors hold their underlying connections open indefinitely. The pool exhausts gradually over 3 hours of accumulated batch runs. The signal is a slow rise in pool utilization across multiple log entries, not a sudden spike. The recommended action is `hotfix` (fix the cursor.close() line) not rollback — testing the agent's ability to distinguish a fixable code bug from a bad-in-concept deploy.

#### downstream_outage_01 — Stripe API down (payment-service)

The payment service itself is completely healthy — no internal errors, no recent deploys, DB pool fine. But Stripe's API is returning 503 on all charge and refund endpoints. The logs explicitly state internal health is nominal and that a fallback processor (Adyen) exists but isn't configured. The correct response is `escalate` to the vendor, not a rollback or hotfix. The deploy list includes a Stripe client library bump from the day before (red herring) — tests whether the agent correctly dismisses it as unrelated.

#### downstream_outage_02 — Internal cascade (api-gateway alert, auth-service root cause)

This is the most adversarial scenario. The alert fires on `api-gateway` (p99 latency 12,400ms), but the root cause is in `auth-service`. A new auth-service deploy adds session activity tracking with an unindexed query on a 2.1M-row sessions table. Under prod load, the query takes 8–12 seconds. Every api-gateway request that requires auth verification waits for auth-service, causing the cascade. The `ground_truth.affected_service` is `auth-service` even though the `alert.service` is `api-gateway`. One log entry explicitly notes that static routes (which bypass auth) respond normally at 12ms — the key clue. This tests whether the agent can look past the alerting surface and find the true root cause one layer deeper.

#### memory_leak_01 — Unbounded query result cache (analytics-pipeline)

A caching feature stores query results in a module-level dict with no max size, TTL, or LRU eviction. Every unique query key persists forever. Under prod query diversity, the cache grows at 22MB/min, taking ~3 hours to reach OOM. The alert fires on `memory_usage_bytes` (not error_rate), testing the agent's ability to handle a non-error-rate metric. The logs show the full progression: 512MB at deploy, 1.1GB after 1 hour, 2.6GB after 2 hours, OOM kill at 4GB, pod restart. A log entry notes the issue will recur after restart — the agent should recommend rollback, not just "wait for restart."

#### memory_leak_02 — WebSocket event listener accumulation (notification-service)

A WebSocket refactor registers `emitter.on('message', handler)` for each new connection but never calls `emitter.off()` on disconnect. Each retained handler holds ~350KB of closure scope. After 4,000+ connections (normal for 3 hours of prod traffic), memory bloats to OOM. The alert fires on `process_restarts_total` (5 restarts > threshold of 2) rather than memory, testing a different alert metric. The CrashLoopBackOff pattern is explicitly logged — each restart clears memory but the leak resumes immediately. This is semantically different from memory_leak_01 (retained objects vs. unbounded cache).

#### config_regression_01 — Feature flag rollout breaks 50% of users (user-service)

The most unusual scenario: there is no code deploy responsible. A ConfigMap update enables the feature flag `enable_new_auth_flow` at 50% rollout. The new auth flow has a parameter order bug in `refresh_token()`. Exactly ~50% of users (determined by user_id hash) hit the failing path; the other 50% succeed on the legacy path. This creates an unusual error rate pattern — partial failure that doesn't look like a full outage. The logs interleave successful and failing requests with the feature flag assignment visible. The deploy list includes a deploy from 6 hours ago that added the new_auth_flow *code* behind the flag (off by default) — a tempting red herring that should not be blamed, since it wasn't the cause. The correct action is `escalate` to disable the flag via config management.

### Key decisions and trade-offs

**`downstream_outage_02` has a split alert/root-cause service** — The alert service (`api-gateway`) differs from `ground_truth.affected_service` (`auth-service`). This is deliberate. A naive agent that just looks at which service is alerting would pick the wrong service. The agent needs to trace the cascade one level upstream. This is the hardest scenario for the Deploy Correlator and Triage agents.

**`db_pool_02` recommends `hotfix` not `rollback`** — The bug (missing `cursor.close()`) is a one-line fix. Rolling back the batch job would also lose the reconciliation functionality. The `hotfix` recommendation tests whether the agent can distinguish "bad design" (rollback) from "implementation bug" (hotfix).

**`config_regression_01` has no deploy_id in either field** — The alerting service had a code deploy 6 hours ago, but that deploy is innocent. The actual cause is a real-time config change (ConfigMap update), which doesn't appear in the deploys array at all. The Deploy Correlator should return `suspect_deploy: None` despite a recent code deploy existing — the timing doesn't match (6 hours gap, not 15 minutes).

**5 distinct failure classes** — The test suite now asserts all 5 classes are present across the 10 scenarios. This ensures the eval grades the agent across a diverse failure taxonomy, not just the easiest (bad_deploy) cases.
