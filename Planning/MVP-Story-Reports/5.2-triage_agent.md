## Plain English Summary

### The Problem

When an alert fires — say "api-gateway error rate is 34%, threshold 5%" — the first thing the system needs to decide is: *how bad is this, really?* A raw alert metric alone doesn't tell you whether to page the entire on-call team at 3am (P1) or just file a ticket for the next working day (P4). You need to know the service tier, whether this same thing happened last week, and what action to take next.

That's the Triage Agent's job: it takes the alert, enriches it with service context and historical incident memory, and returns a clear classification that every subsequent agent depends on.

### What Was Built

**`TriageResult`** is a new Pydantic model added to `models/incident.py`. It has four fields:
- `severity` — P1 through P4 (how urgent is this?)
- `affected_service` — the confirmed service name
- `is_duplicate` — was this same incident already active? (skips re-investigation if true)
- `recommended_action` — a short sentence telling the orchestrator what to do next

Previously, the `Incident` model stored `triage_result` as a raw `dict[str, Any]` with a note "concrete type comes in a later phase." This is that phase — `TriageResult` is the concrete type.

**`build_triage_agent()`** is a factory function in `agents/triage.py` that creates a configured Agent object. The factory pattern is used (rather than a module-level singleton) so that different test contexts can inject different memory clients. The function:

1. Takes the two memory clients the agent needs: `SemanticMemory` (for service lookups) and `EpisodicMemory` (for past incident search).
2. Takes a pre-configured `AsyncOpenAI` client pointed at Groq's base URL — this is the LLM provider.
3. Creates an `OpenAIChatCompletionsModel` wrapping the Groq client with the `llama-3.1-8b-instant` model (the fast classification model, equivalent to gpt-4o-mini in cost/speed).
4. Returns an `Agent` with:
   - Name: `"triage_agent"`
   - Instructions: loaded from `prompts/triage.txt` at runtime
   - Tools: exactly two — `get_service_metadata` and `search_past_incidents`
   - `output_type=TriageResult` — tells the SDK to force the LLM to respond with JSON matching the TriageResult schema

### Key Decisions

**Structured output via `output_type`:** Setting `output_type=TriageResult` on the Agent is important. Without it, the LLM would return a free-text response that downstream code would need to parse (fragile). With it, the Agents SDK uses JSON schema enforcement so the agent always returns a valid `TriageResult` — P1/P2/P3/P4 are the only valid severity values, `is_duplicate` is always a boolean, never a string like "yes". This eliminates an entire class of parse errors.

**Narrow tool scope:** The Triage Agent only has 2 tools — service lookup and incident search. It deliberately does not have `fetch_logs`, `list_recent_deploys`, or any remediation tools. This constraint matters both for cost (fewer tools = smaller prompt = cheaper calls) and for safety (the Triage Agent can't accidentally act on the world).

**Groq client injection:** The `groq_client` is injected rather than created inside the factory. This means the caller (FastAPI lifespan or test) creates one shared `AsyncOpenAI` client and passes it to all agent factories — no duplicate HTTP clients. In tests, a fake API key is passed so the client object can be constructed without making real network calls.

**No handoffs on specialists:** Only the Orchestrator routes between agents. The Triage Agent returns its result and control goes back to the caller — it does not hand off to the Log Analyst itself. This is explicit in the tests: `test_triage_agent_no_handoffs` verifies the handoffs list is empty.
