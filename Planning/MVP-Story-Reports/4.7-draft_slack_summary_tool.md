## Plain English Summary

### What problem it solves

When an incident is being resolved, the on-call team and stakeholders need a clear, consistent status update. A well-structured Slack message in the #incidents channel tells everyone: what's broken, why it's broken, what's being done about it, and when it'll be fixed. Writing this message manually during an incident is error-prone — people forget sections, use inconsistent formatting, or miss context.

`draft_slack_summary` takes the full incident state and formats it into a standardized Slack message template: Impact, Root Cause, Timeline, Current Status, Action Items, and ETA. The Comms Agent calls this tool once it has gathered the full context from the incident pipeline.

### What was built

**Tool signature:**

```
draft_slack_summary(incident_summary: str) -> str
```

**How it works step by step:**

1. **Validate input** — empty or whitespace-only → error string.

2. **Parse the incident data** — `_parse_incident_data()` tries JSON parsing first. If the input is a valid JSON object, it extracts the 8 template keys (service, severity, impact, root_cause, timeline, status, action_items, eta). Missing keys get "N/A". If JSON parsing fails (raw text or non-dict JSON like an array), it falls back to wrapping the raw text in the timeline section, with all other fields set to "N/A".

3. **Format the Slack message** — `_format_slack_message()` applies the standard template using Slack's mrkdwn syntax: bold section headers (`*Impact*`), the `:rotating_light:` emoji prefix, and the service/severity in the header line.

Example output with JSON input:
```
:rotating_light: *Incident Summary* — api-gateway (P1)

*Impact*
500 errors on /api/v1/users, 40% of requests affected

*Root Cause*
NullPointerException in AuthMiddleware from deploy-abc123

*Timeline*
02:44 deploy | 02:45 errors | 02:50 alert | 03:00 investigating

*Current Status*
Rollback PR drafted, awaiting approval

*Action Items*
Review rollback PR, monitor error rate post-merge

*ETA to Resolution*
15 minutes
```

### Key design decisions

- **JSON preferred, raw text as fallback** — the Comms Agent is instructed to pass JSON with the 8 template keys. But if it passes free text instead (early in triage when structure isn't available yet), the tool still produces a valid message rather than failing. The raw text goes into the timeline section, and everything else shows "N/A".

- **No dependencies injected** — like the remediation tools, this is a pure formatter. `make_comms_tools()` takes no arguments. The Comms Agent has already gathered the full incident context from the orchestrator; the tool just applies the template.

- **`cast()` for pyright strict mode** — `json.loads()` returns `Any`, which causes `dict.get()` type errors under pyright strict. `cast(dict[str, object], raw)` after the `isinstance(raw, dict)` check satisfies the type checker without a runtime cost.

- **Partial JSON fills missing keys with "N/A"** — if the LLM passes `{"service": "api-gateway", "severity": "P2"}` without the other 6 keys, the tool fills them as "N/A" rather than crashing. The output is still structured and readable.
