## Plain English Summary

### What problem it solves

Once the Remediation Agent decides what to do — roll back the bad deploy or apply a targeted hotfix — it needs to produce a concrete artifact: something a human engineer can look at, review, and approve. In production, a rollback would mean opening a GitHub PR; a hotfix would mean writing a code change and getting it reviewed.

In the MVP, Sentinel doesn't have GitHub access. So these two tools generate the *content* of those actions — the PR title and body, the diff template, the test suggestions — in a structured, human-readable format. The artifact feeds directly into the HITL approval gate, where a human engineer decides whether to proceed.

**The key invariant: no tool in this layer touches external state.** These tools only *draft* — they never open a PR, never push code, never call an API. That boundary is enforced by design.

### What was built

**Two tools returned as a list from `make_remediation_tools()`:**

```
draft_rollback_pr(deploy_id: str, justification: str) -> str
draft_hotfix(file_path: str, fix_description: str) -> str
```

No dependencies are injected — these tools are pure template generators. `make_remediation_tools()` takes no arguments and returns both tools as a flat list, which `build_tools()` extends into the full registry.

**`draft_rollback_pr` step by step:**

1. Validate both inputs are non-empty (whitespace-only → error string).
2. Derive the branch name: `revert/{deploy_id}`.
3. Derive the PR title: `revert: rollback {deploy_id} (Sentinel auto-draft)`.
4. Build a markdown PR body with:
   - An incident trigger explanation
   - The justification (verbatim from the agent's reasoning)
   - What the PR does (reverts the deploy)
   - A pre-merge checklist (CI, engineer review, monitoring)
   - Post-merge monitoring steps
   - A clear approval warning: "⚠️ This PR was drafted by Sentinel and requires human approval before opening"
5. Return as a formatted string with header fields (title, branch, target, deploy_id) followed by the full body.

**`draft_hotfix` step by step:**

1. Validate both inputs are non-empty.
2. Build a unified diff template (not a real diff — a placeholder with the fix description embedded as a comment, guiding the engineer on what to change).
3. Build test suggestions: a regression test for the failure scenario, a suite run for the changed file, and a smoke test for the affected endpoint.
4. Return as a formatted string with header fields (file, fix) followed by the diff template and test suggestions, ending with the approval warning.

Example `draft_rollback_pr` output:
```
PR DRAFT — deploy-abc123

title:         revert: rollback deploy-abc123 (Sentinel auto-draft)
branch:        revert/deploy-abc123
target:        main
deploy_id:     deploy-abc123

## Rollback PR — deploy-abc123

**Incident trigger:** Sentinel identified this deploy as the likely root cause
of an active incident.

### Justification

NullPointerException in AuthMiddleware.validate() appeared 5 seconds after deploy.

### What this PR does

Reverts `deploy-abc123` to restore the previous stable state of the service.
...

⚠️ This PR was drafted by Sentinel and requires human approval before opening.
```

### Key design decisions

- **No dependencies injected** — unlike `fetch_logs` or `list_recent_deploys`, these tools don't need scenario data, episodic memory, or any other runtime dependency. They take structured text inputs and produce structured text outputs. This is why `make_remediation_tools()` takes no arguments.

- **`make_remediation_tools()` returns a list, not a single tool** — since both tools are always registered together (the Remediation Agent needs both), the factory returns `[draft_rollback_pr, draft_hotfix]` and the registry uses `tools.extend(make_remediation_tools())`. Keeps the two tools coupled at the factory level without requiring two separate factory imports.

- **Diff template, not a real diff** — `draft_hotfix` can't produce an actual unified diff without reading the source file (which would require file system access, credentials, and is outside MVP scope). The template shows the structure with the fix description embedded as a comment. The engineer receiving the approval request knows they need to fill in the exact changes.

- **Approval warning on every artifact** — both tools end with "⚠️ Awaiting human approval before this [PR is opened / hotfix is committed]." This is redundant given the HITL gate, but reinforces the safety boundary for any human reading the draft.

- **Same testability pattern** — logic extracted to `_draft_rollback_pr()` and `_draft_hotfix()` (module-level functions callable without ToolContext). Tests call these directly for content assertions.
