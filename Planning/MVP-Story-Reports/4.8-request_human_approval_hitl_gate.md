## Plain English Summary

### What problem it solves

This is the **critical safety boundary** of the entire Sentinel system. The core design invariant is: no agent can perform a destructive or irreversible action (rollback, hotfix merge, service restart) without a human explicitly approving it. There is no "execute rollback" tool — there are only "draft rollback" tools + this approval gate.

`request_human_approval` is the only path between a drafted action and its execution. Every call is logged with structured logging (action, risk level, who proposed it, what was decided). The gate blocks until a human decides — approve or reject — with an optional comment explaining their reasoning.

### What was built

**Tool signature:**

```
request_human_approval(
    action: str,           # "Roll back deploy-abc123 on api-gateway"
    risk_level: str,       # "high", "medium", or "low"
    evidence_summary: str, # why this action is recommended
    proposed_by: str,      # "remediation_agent"
) -> str
```

**How it works step by step:**

1. **Validate all 4 inputs** — empty or whitespace-only → error string.

2. **Format the display** — `_format_request_display()` builds a terminal-friendly approval card with visual separators, a risk indicator (`!!!` for high risk, `!` for others), and all the request details.

3. **Call the approval handler** — an async callback (`ApprovalFn`) receives the formatted display and returns `(decision, comment)`. In the MVP, `_terminal_approval()` prints the display and collects `input()` via `asyncio.to_thread` (non-blocking). In tests, simple async functions like `_auto_approve` or `_auto_reject` are injected. In Phase 2, a Slack webhook or REST API handler can be swapped in without touching the tool.

4. **Normalize the decision** — "approve" → `APPROVED`, anything else → `REJECTED`. This fail-safe means ambiguous or malformed input always results in rejection, never accidental approval.

5. **Log the decision** — `structlog` captures every decision with the full context: action, risk level, proposer, status, and optional comment. This is an audit trail.

6. **Return formatted result** — the agent receives a clear string with the decision status and all fields, so it knows whether to proceed or halt.

**Terminal display example (high risk):**
```
============================================================
!!! HITL APPROVAL REQUEST !!!
============================================================

Proposed by:  remediation_agent
Risk level:   high

ACTION: Roll back deploy-abc123 on api-gateway

EVIDENCE:
NullPointerException appeared 5s after deploy-abc123

============================================================

>>> Enter 'approve' or 'reject': 
```

### Key design decisions

- **Injectable `ApprovalFn` callback** — the core design decision. `make_hitl_tool(approval_fn=None)` accepts an optional async callback. Default is `_terminal_approval` (MVP terminal input). Tests inject mock callbacks that return immediately. Phase 2 injects Slack/API handlers. The tool interface and agent behavior are completely unaffected by the swap. This is the DI pattern specified in ARCHITECTURE.md §8.

- **Unknown decisions default to REJECTED** — if the human types "maybe", "yes", "ok", or anything other than exactly "approve", the decision is REJECTED. This is a deliberate fail-safe: the cost of accidentally rejecting is low (agent can retry), the cost of accidentally approving is high (irreversible action executes).

- **`asyncio.to_thread(input, ...)` for non-blocking I/O** — `input()` blocks the thread. In an async context, this would freeze the event loop. `asyncio.to_thread` runs it on a worker thread, keeping the loop responsive.

- **structlog audit logging** — every decision is logged at INFO level with structured fields. This creates a queryable audit trail: "show me all REJECTED high-risk actions in the last 24 hours." The TODO explicitly required logging every approval/rejection.

- **Risk indicator in display** — high-risk requests show `!!!` to visually alert the reviewer. Other risk levels show `!`. A small touch, but high-risk approvals in a terminal deserve visual urgency.

*Error handling (5):* Empty action, whitespace action, empty risk_level, empty evidence, empty proposed_by → error strings.
