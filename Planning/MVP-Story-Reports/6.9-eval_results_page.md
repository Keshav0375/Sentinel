## Plain English Summary

### What Problem This Solves

After task 6.8, Sentinel had a live incident dashboard showing the agent pipeline running in real time. But there was no way to see *how well* the agents performed across scenarios. The eval system (Phase 7) will generate scored reports — this task builds the page that displays those scores so you can open a browser and immediately see: "Triage got 4.5/5 on bad_deploy_01 but only 2.0/5 on db_pool_01."

This is the second Loom demo moment: "here's how I grade the agent's performance."

### What Was Built (Step by Step)

#### 1. Eval Report API (`src/sentinel/api/eval_report.py`)

A `GET /api/eval-report` endpoint that reads `reports/eval_report.json` from disk and returns the raw JSON. It reads on every request (no caching) so the page always shows the most recent eval run without restarting the server. If the file doesn't exist yet (eval hasn't been run), it returns 404 with a helpful message telling you to run `python scripts/run_eval.py`.

The endpoint uses dependency injection for the report path, making it testable with `tmp_path` fixtures.

#### 2. Eval Results HTML (`src/sentinel/dashboard/eval.html`)

A self-contained HTML page matching the main dashboard's dark GitHub theme (same CSS variables, same font stack, same color system). No external dependencies.

**Layout has three zones:**

- **Summary cards row**: Four cards showing overall average score (color-coded), total scenarios count, pass rate percentage (pass = total_score >= 3.0), and the judge model name.

- **Per-scenario scores table**: One row per scenario, columns for each of the 6 eval dimensions (Triage, Root Cause, Tool Efficiency, MTTR, Remediation Safety, Comms), plus total score and pass/fail. Each score cell is color-coded: green (>= 4.0), amber (>= 2.5), red (< 2.5). A bold averages row at the bottom shows per-dimension means.

- **Meta line**: Shows when the report was generated.

The page fetches from `/api/eval-report` on load. If the endpoint returns 404, it shows a friendly "no report found" message. The JS handles both `results` and `scores` as the top-level array key for forward compatibility with however the eval runner structures its output.

#### 3. Main.py Updates

Two additions:
- `GET /eval` route returns `eval.html` as an `HTMLResponse` (same pattern as `GET /` for the main dashboard)
- `make_eval_report_router()` included so `GET /api/eval-report` is mounted during lifespan

The main dashboard already had a "View eval results ->" link in the footer (added in 6.8), which now resolves to this page.

### Key Decisions

**Read from disk on every request**: The eval report is generated infrequently (once per eval run). Reading a small JSON file per request is negligible compared to the cost of running the eval suite. This avoids stale-cache bugs and keeps the code simple.

**404 instead of empty page**: If no eval report exists, a clear 404 with instructions is more helpful than rendering an empty table. The HTML gracefully shows a "no report found" message rather than an error.

**Flexible JSON shape**: The frontend accepts both `data.results` and `data.scores` as the array key, so the eval report generator (Phase 7) has flexibility in its output format.

**Pass threshold at 3.0**: Total score >= 3.0 (out of 5.0) marks a scenario as passing. This is a 60% bar — reasonable for an MVP where agents may not be fully tuned yet.
