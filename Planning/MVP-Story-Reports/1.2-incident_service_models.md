## Plain English Summary

### What problem this solves

Once an alert comes in (task 1.1 built the alert models), Sentinel needs a way to track everything that happens to it. Think of an "incident" like a support ticket — it gets created, goes through several stages of investigation, and eventually gets resolved. Every agent action, every finding, every human approval or rejection gets attached to this one central object.

This task also defines what a "service" is in our system — not just a name, but who owns it, what tier it's in, how to reach the on-call team, and what other services depend on it.

### What was built, step by step

**`Severity` enum (P1–P4):**
This is Sentinel's *internal* severity rating, set by the Triage Agent after it has thought about the alert. It's separate from `AlertSeverity` (built in 1.1), which is just the raw level from Datadog or PagerDuty. The distinction matters because "Datadog says critical" doesn't always mean "this is a P1" — for example, a critical alert on a best-effort analytics pipeline might only be P3. The Triage Agent's job is precisely to map one to the other.

**`IncidentStatus` enum:**
Six stages an incident can be in: `triage` (just received) → `investigating` (agents are working) → `remediating` (a fix has been drafted) → `pending_approval` (waiting on a human to approve the fix) → `resolved` (done) or `escalated` (agents couldn't handle it). This is the incident's lifecycle, and the orchestrator moves it forward.

**`TimelineEntry`:**
A small record of one thing that happened: which agent did it, what action they took (a tool call or handoff), and a plain-text summary of what they found. The timestamp defaults to now. These entries get appended in sequence and form the "trajectory" that the eval system later grades.

**`Incident`:**
The main object. It holds:
- The triggering alert (the whole `AlertPayload` from task 1.1)
- A running list of `TimelineEntry` records — the full history of agent steps
- The current status and severity (both optional until the Triage Agent fills them in)
- Five result slots (`triage_result`, `log_analysis`, `deploy_correlation`, `remediation_plan`, `comms_summary`) where each specialist agent deposits its findings
- Creation and resolution timestamps

The ID is auto-generated as `inc-` followed by 8 random hex characters (e.g. `inc-a1b2c3d4`), which is more readable in logs than a full UUID.

The result slots are typed as `dict[str, Any] | None` rather than their eventual proper types (like `LogAnalysis`), because those types don't exist yet — they'll be defined in phases 1.3 and 5.x. This is an intentional placeholder that will be tightened up later.

**`ServiceTier` enum + `ServiceMetadata`:**
A service has three tiers: `critical` (must be available 24/7), `standard` (normal SLA), and `best-effort` (can degrade without a P1 incident). The `ServiceMetadata` model captures everything about a service that agents need to understand blast radius: its name, who owns it, how to reach the on-call person, where the code lives, and which other services it calls (the dependency list). This is loaded from the semantic memory store (SQLite) at the start of each incident.

### Key decisions and trade-offs

**Result fields as `dict[str, Any]`:** The proper model types (`LogAnalysis`, `DeployCorrelation`, etc.) come from tasks 1.3 and the agent phase. Rather than creating stub or circular imports, the result fields are left as untyped dicts for now. This is a conscious compromise — the data is still stored and serialized correctly, and the concrete types will be added once they exist.

**`timeline: list[TimelineEntry] = []`:** Pydantic v2 handles mutable defaults safely (it deep-copies them per instance), so `= []` is both idiomatic and correct. The `Field(default_factory=list)` alternative caused pyright strict mode to report an "unknown variable type" because the bare `list` factory doesn't carry the `[TimelineEntry]` generic information.

**`ServiceTier` added to `service.py`:** Not in the original TODO spec, but the ARCHITECTURE.md table schema (and the Semantic Memory section) defines exactly three tier values. Adding the enum avoids magic strings leaking into comparison logic later.
