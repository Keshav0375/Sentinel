## Plain English Summary

### What problem it solves

Sentinel needed a way to *remember* past incidents so the Triage Agent can learn from history. When a new alert fires — say, "payment-service is throwing connection pool errors" — the agent should be able to ask: "Have we seen something like this before?" and get back the top matching past incidents, complete with what caused them and how they were fixed. Without episodic memory, every incident starts from scratch.

### What was built

**`EpisodicMemory`** is a SQLite-backed store that keeps a record of every resolved incident. Here's how it works step by step:

1. **Storing an incident** (`store_incident`): When an incident is resolved, the system builds a natural language "symptoms" sentence from the incident's alert data — things like the service name, the metric that triggered, the current value vs threshold, and severity. That sentence is passed to the `EmbeddingClient`, which converts it into a 384-dimensional vector of numbers that captures its semantic meaning. The vector is packed into a compact binary blob (using numpy's `tobytes()`) and saved to the `episodic_incidents` table in SQLite alongside the full incident record.

2. **Searching for similar past incidents** (`search_similar`): When a new incident arrives, the agent passes a description of current symptoms as a plain-English string. The system embeds that query into the same vector space, then loads every stored embedding from the database and computes *cosine similarity* between the query vector and each stored vector. Cosine similarity measures the angle between two vectors — two semantically similar descriptions (both about database connection pool issues, for example) will have vectors pointing in nearly the same direction, giving a similarity close to 1.0. Unrelated incidents (memory leaks, deploy errors) will have vectors pointing in different directions, giving similarity close to 0.0. The results are sorted by score and the top-k are returned.

3. **Single internal helper** (`_scored_search`): Both `search_similar` and the protocol's `query()` method share one private `_scored_search` helper that does all the embedding + ranking work. This avoids duplicating the computation while letting the two public methods return different shapes (list vs `MemoryQueryResult` with parallel scores).

4. **Protocol compliance**: `EpisodicMemory` satisfies the `MemoryStore` protocol — `store()` wraps `store_incident()`, `get()` wraps `get_incident()`, `query()` returns a `MemoryQueryResult` with both records and their similarity scores in parallel, and `delete()` removes a record by ID. A runtime assertion at import time catches any future signature drift immediately.

### Key design decisions

- **Embedding as `float32` BLOB**: Storing embeddings as packed binary (4 bytes per float) is compact and fast to deserialize with `np.frombuffer`. No extra tables, no serialization overhead.
- **`_build_symptom_text` derives symptoms from the incident**: Since `Incident` has no explicit `symptoms` field, the system builds one from the alert's metric, service, severity, and any available log analysis hypothesis. This keeps the API clean — callers just pass an `Incident`, and the memory layer handles text construction.
- **Python-level cosine similarity (no vector DB)**: For MVP scale (hundreds of incidents), loading all embeddings and ranking them in numpy is fast enough. A production system would swap this for Cosmos DB or pgvector — but that's a Phase 2 concern.
- **`_KeywordFakeModel` for deterministic tests**: Tests use a fake embedding model that assigns unit vectors based on keywords (e.g., anything containing "connection" or "pool" gets `[1, 0, 0, 0]`). This makes similarity scores exact and deterministic — the core ranking test stores 3 incidents from different failure classes and verifies that the correct one comes first with similarity 1.0, not "approximately higher."
- **MTTR computed on store**: If the incident has a `resolved_at` timestamp, the time-to-resolve is computed in seconds and stored. This feeds the `mttr` eval dimension later.
