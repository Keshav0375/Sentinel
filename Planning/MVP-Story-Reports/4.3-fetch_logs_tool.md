## Plain English Summary

### What problem it solves

When the Log Analyst agent needs to investigate an incident, it has to read actual log lines from the affected service to find error patterns and form a hypothesis about the root cause. In production, this would call Datadog or CloudWatch. In the MVP, we use the pre-loaded scenario data — each scenario file contains a curated set of logs including the "signal" (error messages, stack traces, anomalies) plus background "noise" logs from unrelated services that make the stream feel realistic.

`fetch_logs` lets the agent query this synthetic log stream with the same interface it would use in production: specify a service, a time window, and optional filters, and get back a formatted list of matching log lines.

### What was built

**Tool signature** (flat parameters, `strict_mode=False` for optional defaults):

```
fetch_logs(
    service: str,              # e.g. "api-gateway"
    start_time: str,           # ISO-8601, e.g. "2026-05-10T02:30:00Z"
    end_time: str,             # ISO-8601, e.g. "2026-05-10T03:05:00Z"
    level_filter: str = "",    # e.g. "ERROR" → returns ERROR + CRITICAL
    keyword_filter: str = "",  # case-insensitive substring match
) -> str
```

**How it works step by step:**

1. **Validate inputs** — if `scenario` is None, service is empty, timestamps are unparseable, or start > end, return an error string immediately (tools never raise).

2. **Generate all logs** — calls `generate_logs(scenario, noise=True)` which returns all log entries from the scenario file plus a small set of background INFO logs from unrelated services. For `bad_deploy_01` this is 17 total logs (12 from `api-gateway`, 3 background noise from `cdn-proxy`, `notification-service`, `user-service`).

3. **Filter by service** — keeps only entries where `entry.service == service`. This automatically excludes noise logs when the agent queries the correct affected service.

4. **Filter by time window** — keeps entries where `start_dt ≤ entry.timestamp ≤ end_dt`. The agent typically passes a 30–60 minute window around the alert time.

5. **Filter by level (minimum severity)** — if `level_filter="ERROR"`, uses a severity ordering (`DEBUG=0, INFO=1, WARNING=2, ERROR=3, CRITICAL=4`) to return all entries at ERROR severity or above. This means the agent can ask for "all serious problems" without knowing the exact log levels upfront.

6. **Filter by keyword** — if `keyword_filter="NullPointerException"`, keeps only entries whose message contains that string (case-insensitive). The agent can zero in on a specific error class.

7. **Format the results** — returns a compact multi-line string with one entry per line: `[timestamp] LEVEL    message`. Includes a header with count and time range, and a footer showing how many raw logs were filtered down.

Example output:
```
Found 7 log entries for 'api-gateway' (2026-05-10T02:00:00Z → 2026-05-10T04:00:00Z):
[2026-05-10T02:44:55Z] ERROR    NullPointerException in AuthMiddleware.validate()...
[2026-05-10T02:45:01Z] ERROR    Request failed: /api/v1/users — 500 Internal Server Error
[2026-05-10T02:45:02Z] WARNING  Retrying authentication: attempt 1/3
...
(7 of 17 total logs shown after filtering)
```

### Key design decisions

- **`strict_mode=False`** — the OpenAI Agents SDK's strict mode doesn't allow parameters with default values in the JSON schema. Since `level_filter` and `keyword_filter` should be optional (the agent might not always need them), `strict_mode=False` is required. The trade-off is a slightly less constrained schema, but the required parameters (`service`, `start_time`, `end_time`) are still clearly specified in the docstring.

- **Flat parameters instead of `LogQuery` model** — the `LogQuery` Pydantic model exists for other purposes, but passing a nested model to an LLM tool requires the agent to construct JSON with a specific structure. Flat string parameters are more natural for the LLM to fill in from context.

- **Minimum-level semantics for `level_filter`** — "show me WARNING and above" is a much more natural query than "show me only WARNING-level entries". The severity ordering ensures that an agent asking for ERROR logs also sees CRITICAL entries without needing a second query.

- **Noise is always generated, filtered by service** — `generate_logs` always produces noise (simulating a real log stream where multiple services emit logs simultaneously). By filtering to one service, noise from unrelated services is automatically excluded. This also means the agent gets realistic "false signal" if it queries the wrong service — teaching it to check service names carefully.

- **Extractable helpers for testability** — `_fetch_logs`, `_filter_logs`, `_format_logs`, and `_parse_iso` are all module-level functions callable without a `ToolContext`. Tests invoke these directly rather than going through the SDK tool invocation machinery, making them fast and reliable.

### Test coverage

43 tests in four layers:

*Tool wrapping (7):* `make_log_fetcher_tool` returns `FunctionTool`, correct name, non-empty description, schema has `service`/`start_time`/`end_time`, `scenario` not in schema.

*Error handling (6):* None scenario → error string (no raise), empty service → error, invalid timestamps → error, start > end → error.

*Successful retrieval (8):* Returns string, contains service name in header, correct count (12 api-gateway logs verified against actual scenario data), timestamps in output, log levels visible, known `NullPointerException` message present, unknown service → "No log entries found", window before all logs → "No log entries found", noise services absent when filtering by alert service.

*Level and keyword filtering (6):* ERROR filter excludes INFO, is minimum-severity (ERROR+CRITICAL), WARNING ≥ ERROR in count, case-insensitive; keyword match, keyword case-insensitive, non-matching keyword → no logs, combined level+keyword filter.

*Unit helpers (16):* `_parse_iso` for Z suffix, +00:00 offset, naive → UTC, invalid → ValueError; `_filter_logs` service/time/level/keyword isolation; `_format_logs` empty result, header count, timestamps, levels, footer total count.
