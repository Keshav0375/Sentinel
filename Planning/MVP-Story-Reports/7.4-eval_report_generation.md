## Plain English Summary

### What Problem This Solves

Task 7.3 built the eval runner that fires all 10 scenarios and returns a list of scored results. But those results were scattered: some JSON-building code lived in `scripts/run_eval.py` as private functions. There was no proper library module for turning scores into structured reports. This matters because:

1. The eval dashboard (`GET /eval`, built in 6.9) reads from `reports/eval_report.json` — the shape of that file needs to be well-defined and stable
2. Future code (CI gates, analysis tools) may want to generate or re-read reports without going through the CLI script
3. The duplicate report-building logic in `run_eval.py` was a maintenance liability

Task 7.4 creates a proper `report.py` library module and updates `run_eval.py` to delegate to it.

### What Was Built (Step by Step)

#### 1. `DimensionStats` dataclass

A frozen (immutable) dataclass that holds aggregate statistics for a single eval dimension across all scenarios:
- `dimension`: which of the 6 dimensions
- `avg_score`: mean across all scored scenarios
- `min_score`: worst-performing scenario on this dimension
- `max_score`: best-performing scenario on this dimension
- `scenario_count`: how many scenarios contributed scores

Frozen because once computed from a score list, these stats shouldn't change.

#### 2. `EvalReport` dataclass

The central object the module produces:
- `scores`: the original `TrajectoryScore` list (preserved as-is)
- `dimension_stats`: six `DimensionStats` objects (one per dimension)
- `avg_total_score`: mean of all `total_score` values
- `pass_rate`: fraction of scenarios where `total_score >= pass_threshold`
- `pass_threshold`: the threshold used (default 3.0, configurable)
- `scenarios_run`: count
- `generated_at`: ISO timestamp of when the report was built
- `judge_model`: the judge LLM used (taken from the first score)

#### 3. `build_report(scores, pass_threshold=3.0)`

The factory function. For an empty list, returns a zero-valued report immediately. For a non-empty list, computes per-dimension aggregates by iterating the dimension scores within each `TrajectoryScore`, then returns an `EvalReport`.

#### 4. `to_json_dict(report)`

Serialises an `EvalReport` to the dict format that `GET /api/eval-report` serves to the eval dashboard:
```json
{
  "generated_at": "...",
  "summary": { "scenarios_run": 10, "avg_total_score": 3.7, ... },
  "dimension_stats": [...],
  "results": [TrajectoryScore.model_dump(), ...]
}
```

The `results` key is what the dashboard JavaScript reads to build its table. The `dimension_stats` key is new — the dashboard can use it for the summary cards without re-computing averages on the client.

#### 5. `to_markdown(report)`

Produces a three-section Markdown document:
- **Summary table**: scenarios evaluated, average score, pass rate (with PASS/FAIL label)
- **Dimension Averages table**: avg, min, max for each of the 6 dimensions
- **Per-Scenario Breakdown table**: one row per scenario with all 6 dimension scores and a PASS/FAIL column

This is the document that goes in `reports/eval_report.md` — readable in GitHub or any Markdown viewer.

#### 6. `write_json / write_markdown / write_reports`

Three writer functions:
- `write_json(report, path)` — writes the JSON dict to a file, creating parent dirs automatically
- `write_markdown(report, path)` — writes the Markdown string to a file, creating parent dirs
- `write_reports(report, reports_dir, json_filename, md_filename)` — convenience wrapper that calls both and returns `(json_path, md_path)`

#### 7. `scripts/run_eval.py` cleanup

The CLI script had three private functions (`_build_json_report`, `_build_md_report`, `_write_reports`) that duplicated the logic now in `report.py`. These were removed and replaced with:
```python
report = build_report(scores_from_results(results))
json_path, md_path = write_reports(report, reports_dir=_REPORTS_DIR)
```

The terminal summary table (printed to stdout) still uses `summary_stats()` from `runner.py` because it includes `failure_rate` (pipeline errors) which `report.py` doesn't track — that's pipeline diagnostic info, not a score metric.

### Key Decisions

**`report.py` takes `list[TrajectoryScore]`, not `list[EvalRunResult]`**: The report is about the *scored results*, not the pipeline metadata. The `pipeline_error` field on `EvalRunResult` is runner-level diagnostics. Keeping the report module's input type to `TrajectoryScore` makes it reusable for any source of scores (not just the batch runner).

**Frozen dataclasses**: Both `DimensionStats` and `EvalReport` are `@dataclass(frozen=True)`. Reports are computed once from a snapshot of scores — mutability would allow the report to drift out of sync with its source data.

**`pass_threshold` is configurable**: The default 3.0 (60% of 5.0) is the right MVP bar, but different teams may want stricter/looser thresholds without code changes. Passing it as a parameter avoids hardcoding.

**JSON shape matches dashboard expectations**: The `results` key and each result's fields (`scenario_id`, `dimension_scores`, `total_score`, `judge_model`) were already validated by the task 6.9 dashboard test suite. The new `dimension_stats` key is additive and backward-compatible.
