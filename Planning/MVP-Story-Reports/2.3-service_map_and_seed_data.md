## Plain English Summary

### What problem this solves

The Triage Agent and Remediation Agent need to know the world they're operating in: which services exist, who owns them, which calls which, and what to do when each fails. Without this seed data, the semantic memory subsystem (to be built in Phase 3) has nothing to load. This task defines that world as static JSON files that the seed.py script (task 2.6) will load into SQLite for runtime use.

### What was built, step by step

#### service_map.json — 8 services

Each service entry captures everything the Triage Agent needs to quickly understand impact and escalation path:

- **api-gateway** (critical, team-platform) — the edge proxy. Everything authenticated goes through it, so it has the widest blast radius. Depends on auth-service, user-service, payment-service, order-service.
- **user-service** (critical, team-identity) — user accounts and profiles. Has no outbound service dependencies — it is a leaf node that other services call into. This is intentional: auth-service calls user-service for user lookups, so making user-service depend on auth-service would create a circular dependency.
- **auth-service** (critical, team-identity) — token issuance and validation. Called by api-gateway on every single authenticated request, making its latency directly proportional to api-gateway's latency. Depends on user-service.
- **payment-service** (critical, team-payments) — Stripe integration. PCI-scoped, no service-to-service dependencies (calls external Stripe API only). The most dangerous service to touch.
- **order-service** (critical, team-commerce) — order lifecycle. Synchronously calls payment-service (blocking) and asynchronously calls notification-service (non-blocking).
- **notification-service** (standard, team-comms) — email/push/WebSocket. Non-critical path: order placement succeeds even if notification delivery fails.
- **analytics-pipeline** (best-effort, team-data) — BI reporting. Reads from read replicas. No user-facing flows depend on it.
- **cdn-proxy** (standard, team-platform) — Cloudflare-backed. Sits in front of api-gateway; api-gateway does not depend on it.

#### dependency_graph.json — 12 directed edges

Each edge captures the direction of the call, the protocol (http or db-read), the criticality level, and a notes field explaining the operational consequence. The critical edges are:
- `api-gateway → auth-service` — every authenticated request; latency here cascades to all routes
- `order-service → payment-service` — synchronous, blocking; payment failure blocks order creation
- `auth-service → user-service` — user lookup on every token verification

The `criticality` field on each edge tells the Triage Agent how to weight the cascade risk. An outage on the critical path through api-gateway → auth-service → user-service affects every user; an outage on analytics-pipeline → order-service only affects reporting.

#### runbooks.json — 19 runbooks

A runbook for every (service, failure_class) combination that appears in the 10 scenarios. Each runbook has 4-7 concrete, actionable steps that reference real kubectl commands, log search patterns, and GitHub URLs. Key design decisions:

- **payment-service runbooks include a PCI warning** — any rollback on a PCI-scoped service needs notification to #oncall-payments first, not just a blind `kubectl rollout undo`.
- **downstream_outage_01 runbook says "Do NOT attempt rollbacks"** — explicitly capturing that external vendor outages are not solvable with internal code changes. This is the kind of guidance an agent needs to avoid recommending a pointless rollback.
- **config_regression runbook** covers the feature flag disable path — "disable the suspect feature flag" before investigating the underlying bug. This matches the scenario where a flag was enabled via ConfigMap update, not a code deploy.

#### Cross-validation in tests

The most important test is `test_runbooks_cover_scenario_failure_classes`: it loads all 10 scenario files, extracts each scenario's `(affected_service, failure_class)` pair from `ground_truth`, and verifies a runbook exists for every combination. This ensures the seed data is coherent with the scenario data — if a new scenario is added without a corresponding runbook, the test fails immediately.

The `test_service_map_deps_consistent_with_graph` test verifies that every service listed as a dependency in service_map.json has a corresponding directed edge in dependency_graph.json. This caught the cdn-proxy direction error (cdn-proxy → api-gateway, not api-gateway → cdn-proxy) and the user-service circular dependency during development.

### Key decisions and trade-offs

**Added runbooks.json beyond the TODO spec** — The TODO said "service_map.json + dependency_graph.json + runbook references." Rather than just listing runbook IDs as references (which would be unusable without the content), the full runbook content was included in runbooks.json. Task 2.6 (seed.py) needs to insert this data anyway — having it here keeps the data co-located with the rest of the seed data.

**user-service has no dependencies** — Removing `auth-service` from user-service's dependency list eliminated a circular dependency (auth-service → user-service → auth-service). This is also architecturally correct: user-service is a data service that exposes an internal API; it doesn't call auth-service.

**Dependency graph `notes` field** — Not in the ARCHITECTURE.md schema, added here because "auth-service → user-service for user lookup" is much more useful to an agent than just a directed edge. When the Triage Agent sees an api-gateway latency alert, the notes on the `api-gateway → auth-service` edge explain exactly why auth-service latency cascades.
