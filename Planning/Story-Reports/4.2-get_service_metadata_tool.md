## Plain English Summary

### What problem it solves

When an alert fires, the first thing the Triage Agent needs to know is: "Who owns this service? What tier is it? What does it depend on? And if something like this has broken before, what's the playbook?" Without this information, the agent is flying blind — it can't assess blast radius, know which team to loop in, or know what remediation steps to follow.

`get_service_metadata` gives the agent instant access to the full service profile: ownership, criticality tier, on-call channel, downstream dependencies, and a preview of available runbooks for common failure classes.

### What was built

The tool is a thin `@function_tool` wrapper around two private helper functions:

**`_build_service_response(memory, service_name) -> str`**  
The core logic. It calls `memory.query(service_name)` which returns a `SemanticRecord` — a bundle of `ServiceMetadata` plus all runbooks for that service in a single database read. If the service doesn't exist, it catches the `KeyError` and returns an error string (tools never raise — they return errors as strings so the LLM can read them and adapt).

**`_format_record(record: SemanticRecord) -> str`**  
Converts the structured `SemanticRecord` into a human-readable multi-line string that the LLM agent can parse and reason about. The format looks like this:

```
name: payment-service
team: team-payments
tier: critical
oncall_channel: #oncall-payments
repo_url: https://github.com/acme/payment-service
description: Handles all payment processing and billing
dependencies: none
runbooks (2):
  [db_pool] Check connection pool config → Check for long-running queries → Restart connection pool ... (5 steps total)
  [downstream_outage] Check external payment API status → Enable fallback mode ... (4 steps total)
```

Each runbook shows up to 3 steps as a preview with `→` separating them. If the runbook has more than 3 steps, the preview ends with `(N steps total)` so the agent knows more detail exists.

**Why a string instead of a Pydantic model?**  
The LLM needs to read and reason about the response, not parse it programmatically. A structured JSON blob (`{"name": "payment-service", "team": "team-payments", ...}`) would work but requires the LLM to decode it. A compact multi-line string is more directly readable by the model and also by humans debugging agent traces. The pattern stays consistent across all tools in this codebase.

**Why two helper functions?**  
The `@function_tool` decorator from the OpenAI Agents SDK requires a `ToolContext` argument to invoke the tool properly, making the tool hard to test directly. By separating the business logic into `_build_service_response` (async, calls memory) and `_format_record` (sync, pure formatting), both can be called directly in tests without any SDK machinery. The tool decorator just calls the helper — it has no logic of its own.

### Key design decisions

- **Error as string, not exception** — CLAUDE.md mandates that tools catch exceptions and return error strings. An unknown service returns `"ERROR: Service 'x' not found in the service map."` which the LLM can read and handle gracefully (e.g., try a different service name or escalate).
- **3-step runbook preview** — showing the first 3 steps tells the agent what kind of remediation is available without overwhelming it with the full playbook. The `(N steps total)` suffix hints that more detail exists if the agent needs to go deeper.
- **`memory.query()` returns both metadata and runbooks** — rather than making two separate calls (`get_service()` + `get_all_runbooks()`), `memory.query()` returns a `SemanticRecord` with both in one round-trip. Fewer DB calls means faster tool execution.
- **Memory dep captured in closure** — the `SemanticMemory` instance is captured in the `@function_tool` closure. The LLM only sees `service_name` as an input parameter — the dep is invisible to the model.

### Test coverage

34 tests in two layers:

*FunctionTool layer (5 tests):* Verify `make_service_lookup_tool` returns a `FunctionTool`, the tool name is exactly `"get_service_metadata"`, it has a non-empty description, the params schema includes `service_name`, and the injected `memory` object does NOT appear in the schema.

*Integration layer (15 tests):* Against a real seeded SQLite database. Verify that responses for all 8 services include service name, team, tier, on-call channel, and runbooks. Test specific pairs: `api-gateway` has `bad_deploy` runbook, `payment-service` has `db_pool` runbook, `analytics-pipeline` has `memory_leak` runbook. Test `user-service` shows "none" for dependencies (it's a leaf service). Test unknown service returns an error string and does not raise.

*Unit formatting layer (14 tests):* Against synthetic `SemanticRecord` objects. Verify `_format_record` produces correct output for each field: name, team, tier, dependencies (including empty → "none"), missing oncall → "none", missing repo → "unknown", runbook failure classes, step previews (exactly 3 shown, truncation message at N+1 steps), multiple runbooks all present, multiline output, runbook count in header.
