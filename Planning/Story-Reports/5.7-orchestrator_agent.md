## Plain English Summary

### The Problem

We now have five specialist agents — Triage, Log Analyst, Deploy Correlator, Remediation, Comms — each excellent at their specific job but knowing nothing about each other. Something needs to receive the incoming alert, send it to the right specialist at the right time, and collect the results into a final incident report.

That something is the Orchestrator. It's the conductor of the whole operation: it knows the order of operations, the conditions for shortcuts, and when the pipeline is done. All the other agents are specialists; the Orchestrator is the manager.

### What Was Built

**`IncidentSummary`** is a new Pydantic model added to `models/incident.py`. It's the final output the entire pipeline produces — the "what happened" report:
- `status` — `"resolved"`, `"pending_approval"`, or `"escalated"` (only these three terminal states, enforced by `Literal`)
- `affected_service` — the confirmed service name from triage
- `severity` — P1 through P4
- `root_cause_summary` — one sentence distilling all the log and deploy analysis
- `action_taken` — what was approved and executed (or `"none"` if escalated)
- `next_steps` — any remaining items (post-mortem, monitoring to watch, etc.)

The `status` field uses Python's `Literal` type instead of an enum, which means Pydantic rejects any value not in the allowed set at parse time — the test `test_incident_summary_rejects_invalid_status` confirms this.

**`build_orchestrator_agent()`** is a factory function in `agents/orchestrator.py` that wires the entire pipeline together. It's the only place in the codebase where all five specialists appear together. The function:

1. Takes the five pre-built specialist agents as arguments (they're built elsewhere and injected).
2. Takes a Groq `AsyncOpenAI` client and model name.
3. Creates an `OpenAIChatCompletionsModel` with `llama-3.3-70b-versatile` — the large reasoning model. The Orchestrator makes judgment calls (when to skip steps, when to escalate, how to synthesize the specialists' outputs into a final summary), which requires stronger reasoning than classification tasks.
4. Returns an `Agent` with:
   - Name: `"incident_orchestrator"`
   - Instructions: loaded from `prompts/orchestrator.txt`
   - **Handoffs** (not tools): the five specialist agents in workflow order
   - `output_type=IncidentSummary` — structured final output
   - **Zero direct tools** — the orchestrator routes, it doesn't act

**`SPECIALIST_ORDER`** is a module-level tuple that documents the canonical pipeline order:
```python
SPECIALIST_ORDER = (
    "triage_agent",
    "log_analyst_agent",
    "deploy_correlator_agent",
    "remediation_agent",
    "comms_agent",
)
```
The test `test_orchestrator_handoff_order` verifies the handoffs are wired in exactly this order, not just that all five names are present. Order matters: the Orchestrator's system prompt tells it to run Triage first, then Log Analyst, and so on. If the handoffs were registered in the wrong order, the LLM's routing decisions could be confused.

### Key Decisions

**Pre-built specialists as arguments:** The factory takes the five already-constructed specialist agents rather than building them internally. This is the cleanest dependency injection pattern — each specialist has its own constructor with its own dependencies (memory clients, scenarios, approval callbacks). If the Orchestrator built them all, it would need to know every dependency of every specialist, making it a god object. Instead, the caller builds the specialists and passes them in.

**No tools on the Orchestrator:** Every other agent has at least one tool; the Orchestrator has zero. This is intentional — the Orchestrator's job is to *delegate*, not to act. It hands off to the Triage Agent to classify, to the Log Analyst to fetch logs, to the Remediation Agent to get approval. If the Orchestrator had tools, it might try to short-circuit the specialist pipeline and call tools directly, defeating the separation of concerns.

**Handoffs vs. tools in the SDK:** The Agents SDK distinguishes between `tools` (functions the agent calls and gets a response from) and `handoffs` (other agents the current agent transfers control to). When the Orchestrator hands off to Triage, Triage runs its full agentic loop (potentially calling multiple tools) and then returns its `TriageResult`. Control returns to the Orchestrator, which then decides the next step. This is different from calling a tool — it's full agent delegation.

**`llama-3.3-70b-versatile` for routing:** The Orchestrator reads the results from each specialist and decides what to do next. It needs to understand complex conditions: "If triage says is_duplicate=true, skip ahead. If deploy correlation returns confidence < 0.3, tell remediation to escalate." This is more nuanced than any single specialist's job.

**Test isolation with `_dummy_agent`:** The orchestrator tests don't require real memory databases or scenario files. A minimal `_dummy_agent` helper creates real `Agent` objects with the right names but no real tools or memory — sufficient to verify that the orchestrator's handoff wiring is correct. This keeps the test suite fast (16s for 26 tests) without sacrificing meaningful structural coverage.
