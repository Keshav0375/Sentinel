## Plain English Summary

### The Problem

Once an incident is resolved — or even while it's still in progress — engineers and managers who weren't part of the response need to be informed. What happened? Which service was affected? What was the root cause? What action was taken? When will it be fully resolved?

Without a structured communications step, the on-call engineer would have to write this Slack message themselves, in the middle of an incident, while also managing the fix. That's where the Comms Agent comes in — it takes everything the other agents discovered and produces a clean, formatted incident summary ready to post to the `#incidents` Slack channel.

### What Was Built

**`SlackSummary`** is a new Pydantic model in `models/comms.py`. It has two fields:
- `slack_message` — the full, formatted Slack message in mrkdwn syntax (bold headers, backtick code spans, emoji severity indicators)
- `recipients` — the list of Slack channels to post to, defaulting to `["#incidents"]`. P1 and P2 incidents also include the affected service team's on-call channel (e.g., `"#oncall-platform"`).

**`build_comms_agent()`** is a factory function in `agents/comms.py` that creates the Comms Agent. The function:

1. Takes a Groq `AsyncOpenAI` client.
2. Creates an `OpenAIChatCompletionsModel` with `llama-3.1-8b-instant` — the fast model. Drafting a structured Slack message from a given incident summary is a formatting task, not a complex reasoning task. The smaller model is the right choice for speed and cost.
3. Returns an `Agent` with:
   - Name: `"comms_agent"`
   - Instructions: loaded from `prompts/comms.txt`
   - Tools: exactly **one** — `draft_slack_summary`
   - `output_type=SlackSummary` — structured JSON with the message text and recipient channels

**The six required sections** that every Slack summary must contain are enforced at three levels:
1. The `draft_slack_summary` tool template always includes them
2. The `comms.txt` system prompt lists them explicitly
3. The test `test_comms_agent_instructions_mention_required_sections` verifies all six appear in the prompt: Impact, Root Cause, Timeline, Current Status, Action Items, ETA

### Key Decisions

**`SlackSummary` over a raw string:** The other agents all use structured output types. Keeping the Comms Agent consistent means the Orchestrator always gets a predictable, typed result — it can extract `slack_message` directly rather than treating the entire agent output as opaque text. The `recipients` field also matters: the Orchestrator needs to know which channels to post to, and that logic belongs in the agent (based on severity), not in the Orchestrator itself.

**One tool only:** Unlike the Log Analyst (2 tools) or Remediation Agent (3 tools), the Comms Agent has exactly one. It doesn't need service metadata, log data, or deploy history — the Orchestrator passes the full incident context as input text. The agent's only job is to call `draft_slack_summary` with that context and return the formatted result. Tool scope reflects job scope.

**Fast model for a formatting task:** `llama-3.1-8b-instant` (same model as Triage) is entirely adequate for taking structured incident data and reformatting it into Slack mrkdwn. Using the larger `llama-3.3-70b-versatile` here would waste tokens and increase latency for no quality gain.

**`list[Tool]` annotation:** Same fix as the Remediation Agent — `make_comms_tools()` returns `list[FunctionTool]` which is not directly assignable to `list[Tool]` due to Python's list invariance. The annotation `tools: list[Tool] = [*make_comms_tools()]` resolves the pyright error cleanly.
