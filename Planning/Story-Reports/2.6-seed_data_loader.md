## Plain English Summary

### What problem this solves

All the service and runbook data defined in Phase 2.3 lives as JSON files. The agents need it in SQLite — that's what the semantic memory subsystem (Phase 3) queries at runtime. The seed script is the bridge: it reads the JSON files and loads them into the three SQLite tables (`episodic_incidents`, `services`, `runbooks`) the rest of the system expects.

### What was built, step by step

#### data/__init__.py

An empty package marker that makes `data` a Python package. This enables `python -m data.seed` to work as a module invocation from the project root, consistent with the other CLI scripts (`python -m data.seed`, `python scripts/run_eval.py`).

#### data/seed.py — `seed(db_path, *, verbose=True) -> tuple[int, int]`

The function does four things in order:

**1. Create tables.** Calls `create_tables(db_path)` from `sentinel.infra.db`, which runs the idempotent `CREATE TABLE IF NOT EXISTS` DDL for all three tables. It also creates parent directories if they don't exist — so `seed(Path("./data/sentinel.db"))` works even if `data/` doesn't exist yet.

**2. Load JSON files.** Reads `data/services/service_map.json` and `data/services/runbooks.json` using paths resolved relative to `__file__`. This makes the script work regardless of the working directory it's launched from.

**3. Insert services.** Each service from the JSON is inserted with `INSERT OR REPLACE INTO services`. The `dependencies` list is serialized to a JSON string before insertion (SQLite stores it in a JSON column; consumers call `json.loads()` to get the list back). Services must be inserted before runbooks because of the foreign key constraint.

**4. Insert runbooks.** Each runbook's `steps` list is similarly serialized to JSON and inserted with `INSERT OR REPLACE INTO runbooks`. The FK constraint on `service_name` is enforced because `create_tables` enables WAL mode and foreign keys on every connection.

The function returns `(services_count, runbooks_count)` so callers can log or assert on the numbers. The `verbose` flag prints a one-line summary to stdout, useful when running the script manually.

#### `__main__` block

Accepts an optional positional argument for the database path:
```
python -m data.seed                        # → ./data/sentinel.db
python -m data.seed ./data/test.db         # → custom path
```

This allows CI or staging environments to seed a different database without touching config files.

### Key decisions and trade-offs

**`INSERT OR REPLACE` instead of `INSERT OR IGNORE`** — `INSERT OR REPLACE` updates an existing row if the primary key already exists. This means re-running the seed after updating `service_map.json` or `runbooks.json` will pick up the changes. `INSERT OR IGNORE` would silently skip updates. The tests verify that running seed twice produces exactly the right row counts (no duplicates, no missing updates).

**Services before runbooks** — The runbooks table has a foreign key `FOREIGN KEY (service_name) REFERENCES services(name)`. Inserting a runbook before its service would raise an FK violation if FK enforcement is on. The seed function always inserts all services first, then all runbooks — the tests verify the FK constraint is satisfied with a LEFT JOIN query.

**JSON paths relative to `__file__`** — Using `Path(__file__).parent / "services"` instead of a relative path like `Path("data/services")` means the script finds its data files correctly whether run as `python -m data.seed` from the project root, or called from a test with `tmp_path`. No environment variable or config setting needed.

**`verbose` parameter** — The function accepts `verbose=False` so tests can call it cleanly without cluttering test output. The `__main__` block always uses the default `verbose=True`. This is a minor ergonomic choice but makes the test file neater.
