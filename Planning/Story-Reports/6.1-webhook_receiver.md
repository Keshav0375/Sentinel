## Plain English Summary

### The Problem

Every incident starts with an alert — a monitoring system like Datadog or PagerDuty fires an HTTP request saying "something is wrong with api-gateway." The system needs a front door to receive these alerts, assign them a tracking ID, and kick off the pipeline. This is the webhook receiver.

But monitoring systems have a reliability quirk: they often deliver the same alert multiple times in quick succession (retry logic, at-least-once delivery guarantees). If the system naively spawned a new pipeline run for every delivery, you'd have parallel incident investigations running simultaneously for the same underlying problem. That's wasteful and confusing.

### What Was Built

**`AlertDeduplicator`** is an in-memory idempotency cache. When an alert arrives with `alert_id = "alert-abc"`, the deduplicator answers two questions:
1. Have we seen this `alert_id` before? (`check()`)
2. Record that we've seen it. (`record()`)

Under the hood it's a Python dict mapping `alert_id → (incident_id, timestamp)`. The timestamp uses `time.monotonic()` — a clock that only moves forward, immune to system clock adjustments — to enforce the 60-second TTL. If a cache entry is older than 60 seconds, it's evicted on the spot when `check()` is called. The `evict_expired()` method can clean up in bulk (useful for long-running processes).

**`make_alert_router()`** is a factory that creates a FastAPI `APIRouter` with the `POST /webhooks/alert` route registered. The factory pattern is used instead of module-level globals so that tests can inject different deduplicators, short-term memory instances, and pipeline callbacks without any mocking framework.

**The route handler** (`receive_alert`) follows this logic on every incoming `AlertPayload`:

1. **Dedup check**: Call `deduplicator.check(alert_id)`. If there's a match within the 60s window, return `202 Accepted` immediately with the *same* `incident_id` as the original — no new incident, no new pipeline run.

2. **New alert path**: Generate a fresh `incident_id` (same `"inc-{8hex}"` format as the `Incident` model). Record the mapping in the deduplicator. Create the incident in `ShortTermMemory`. Log the receipt with structured logging (alert_id, incident_id, service, severity).

3. **Background pipeline**: If a `pipeline_fn` is configured, queue it as a FastAPI `BackgroundTask`. This means the HTTP response is returned immediately (non-blocking 202) and the orchestrator pipeline runs after the response is sent. If no `pipeline_fn` is wired yet (during development of isolated layers), the route logs a warning and returns 202 normally — the API still works, the pipeline just doesn't run.

4. **Return `AlertAck`**: The `AlertAck` Pydantic model (alert_id + incident_id + received_at) is serialized as the 202 response body.

### Key Decisions

**`PipelineFn` as an injectable callback:** Rather than importing the orchestrator directly, the route factory accepts `pipeline_fn: Callable[[str, AlertPayload], Awaitable[None]] | None`. This is the dependency injection pattern applied to the pipeline itself — the main app's lifespan handler (task 6.3) will build the orchestrator and wrap it in a closure matching this signature. This means 6.1 is independently testable without any LLM infrastructure.

**`time.monotonic()` for TTL:** System clocks can jump (NTP sync, VM migration, daylight saving). `monotonic()` is guaranteed to only increase and only measure elapsed time — exactly what a TTL cache needs. Using `datetime.now()` would create subtle bugs in production.

**`BackgroundTasks` over threads/asyncio.create_task:** FastAPI's `BackgroundTasks` is the idiomatic way to queue work that happens after the response is sent. It integrates with FastAPI's lifecycle and error handling. The alternative (`asyncio.create_task` directly) would work but bypasses FastAPI's request lifecycle hooks.

**`# pyright: ignore[reportUnusedFunction]`:** Inner functions decorated with `@router.post(...)` are registered as route handlers through the decorator — they're not unused, they're registered. But pyright in strict mode sees a local function that's never called directly and flags it as `reportUnusedFunction`. This is a known false positive with FastAPI's decorator-based registration pattern. A one-line suppression comment is cleaner than restructuring the whole router.

**`_post_alert` test helper:** All route tests use a shared `_post_alert(client, payload)` helper that calls `json=payload.model_dump(mode="json")`. This ensures `Content-Type: application/json` is always set (FastAPI's `TestClient` requires it for Pydantic model parsing) and `datetime` fields are serialized correctly via Pydantic's JSON mode.
