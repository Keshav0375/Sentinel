## Plain English Summary

### What problem this solves

The `fetch_logs` and `list_recent_deploys` tools (Phase 4) need something to call in the MVP — there's no real Datadog or deployment system. These generator modules bridge that gap: they take a loaded Scenario and produce typed `LogEntry` and `Deploy` objects that the tools can return. The agent pipeline works end-to-end without any external dependencies.

### What was built, step by step

#### log_gen.py — `generate_logs(scenario, noise=True)`

The function has two jobs: conversion and optional noise injection.

**Conversion** maps each `ScenarioLogEntry` to a `LogEntry`, handling the field name difference: `ts` in the JSON becomes `timestamp` in the model. Every other field (`level`, `service`, `message`, `trace_id`) maps directly.

**Noise injection** adds a small number of INFO-level background log lines from unrelated services, interspersed with the real signal. This is what makes the log stream feel realistic — in production, you never get a log stream that contains only the failing service. The noise entries are:
- Always `LogLevel.INFO` (never WARNING/ERROR — that would look like signal)
- Never from the alerting service or the true root-cause service (both excluded)
- Spaced evenly through the scenario's time window so they fall naturally between signal entries
- **Deterministic** — same scenario always produces the same noise entries, no random seed needed

The exclusion of both `alert.service` and `ground_truth.affected_service` matters for `downstream_outage_02`, where these two are different services (api-gateway alerts, auth-service is the root cause). Both are excluded from noise.

The combined list is sorted by timestamp before returning so callers always get a chronological stream.

#### deploy_gen.py — `generate_deploys(scenario)`

Maps each `ScenarioDeploy` to a `Deploy`, handling two field name differences:
- `ts` → `timestamp`
- `commit` → `commit_sha` (with `"n/a"` fallback for null commits — occurs when a config-map change has no associated commit SHA)

Returns deploys sorted **most-recent-first** — the same order a real deployment API returns history. This is important for the Deploy Correlator agent: it sees the most suspicious deploy (the most recent one) at the top of the list without any additional sorting.

### Key decisions and trade-offs

**Deterministic noise, no random seed** — Instead of using `random.choice` with a seed, noise services and messages are selected by index from a fixed ordered pool after filtering out the excluded services. This means the noise output is fully reproducible given the same scenario, which makes tests straightforward: no need to set a seed, mock the RNG, or deal with flaky assertions.

**Three noise entries per scenario** — The pool yields up to 3 entries (the first 3 non-excluded services from `_NOISE_SERVICE_POOL`). Three is enough to break up the signal without overwhelming it. The number was chosen to be smaller than the scenario's own log count (~14) so noise is a minority, not the majority.

**"n/a" for null commit_sha** — `Deploy.commit_sha` is a required `str` field, not nullable. Rather than making the model nullable (which would ripple into the Deploy Correlator's logic), a sentinel string `"n/a"` is used. The Deploy Correlator will see this and know there's no commit to inspect — which is correct for config-change scenarios where there is genuinely no code commit.

**Noise excludes root-cause service, not just alert service** — For `downstream_outage_02` (alert on api-gateway, root cause in auth-service), if we only excluded the alert service, we might inject noise from auth-service. That would look like suspicious signal, not noise. Excluding both is the safer default.
