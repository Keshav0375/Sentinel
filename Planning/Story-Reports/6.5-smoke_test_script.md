## Plain English Summary

### The Problem

The agent pipeline is now fully built: prompts, specialist agents, orchestrator, API layer, tracing. But has it ever actually *run*? All the tests verify structure and individual components, but no automated test has ever fired the orchestrator and watched the full chain execute.

The smoke test script is the "does it work?" checkpoint. You run `python scripts/run_scenario.py bad_deploy_01` and watch: triage classifies severity, log analyst fetches logs and forms a hypothesis, deploy correlator ranks the deploys, remediation drafts a rollback PR and asks for your approval, comms produces a Slack summary. If it doesn't crash and the timeline looks reasonable, the pipeline works.

The task description says "don't proceed to eval until 3+ scenarios pass cleanly" — this script is how you verify that.

### What Was Built

**`scripts/run_scenario.py`** is a self-contained CLI tool with three modes:

```
python scripts/run_scenario.py bad_deploy_01       # fire a scenario
python scripts/run_scenario.py --list              # show all available scenarios
python scripts/run_scenario.py --help              # show usage
```

**What happens when you fire a scenario:**

1. **Load scenario** — reads `data/scenarios/bad_deploy_01.json`, validates it against the Pydantic schema, generates a fresh `AlertPayload` with a new `alert_id` and current timestamp.

2. **Setup** — creates SQLite tables, seeds the service map and runbooks, builds all three memory clients (embedding model, semantic memory, episodic memory, short-term memory), creates the Groq client.

3. **Build agents with scenario injected** — this is the crucial difference from `main.py` (production mode). Here, the `Scenario` object is passed directly into `build_log_analyst_agent(semantic_memory, scenario, ...)` and `build_deploy_correlator_agent(scenario, ...)`. This means `fetch_logs` and `list_recent_deploys` return the synthetic log and deploy data from the scenario file, not error messages about "no scenario loaded." Without this injection, the agents would produce useless results.

4. **Register tracer** — creates a `SentinelTracer` and registers it via `add_trace_processor`. Wraps `Runner.run` with `with agent_trace("incident_pipeline", metadata={"incident_id": incident_id})` so every tool call and handoff gets captured.

5. **Run orchestrator** — calls `Runner.run(orchestrator, input_text, max_turns=15)` inside the trace context. HITL prompts appear in the terminal when the Remediation Agent calls `request_human_approval` — you type `approve` or `reject` and hit Enter.

6. **Print timeline** — after the pipeline completes (or errors), prints every `TimelineEntry` from STM: which agent called which tool at what time, with a truncated output summary.

7. **Print ground truth** — shows the scenario's expected severity, affected service, root cause, and recommended action so you can compare against what the agents actually did.

**Helper functions** extracted for testability:
- `_print_header(title)` — prints a section separator
- `_print_timeline(stm, incident_id)` — prints the formatted timeline
- `_usage()` — prints CLI help text
- `run_scenario(scenario_id, *, db_path=None, trajectories_dir=None)` — async main function

### Key Decisions

**Scenario injection vs. no-op tools:** Production mode (`main.py`) builds agents with `scenario=None`, so `fetch_logs` and `list_recent_deploys` return error messages if called without real data. The smoke test script injects the scenario so the tools return actual synthetic data. This is the correct design — production uses real APIs; smoke test uses synthetic data. Two modes, one agent definition.

**`importlib.util.spec_from_file_location` in tests:** The script lives in `scripts/` which isn't on the pytest Python path (only `src/` is). Rather than modifying `pyproject.toml` or using subprocess, the test file imports the script using Python's `importlib` machinery. This keeps the script as a standalone executable while still making its functions testable.

**FileNotFoundError before any network calls:** `run_scenario()` calls `load_scenario(scenario_id)` as its first step. If the scenario doesn't exist, `FileNotFoundError` is raised immediately — before touching the database, before loading the embedding model, before making any API call. The test `test_run_scenario_raises_file_not_found_for_unknown_id` verifies this fast-fail behavior.

**`--list` flag for discoverability:** Without knowing the available scenario IDs, the script is hard to use. `--list` prints all `data/scenarios/*.json` filenames. The error path (unknown scenario) also prints available scenarios to stderr. This makes the script self-documenting.

**`configure_logging("WARNING")`:** The pipeline emits a lot of structlog INFO messages (agent starts, tool calls, memory lookups). During a demo, these would bury the HITL prompts in noise. Setting the log level to WARNING in the script keeps the output clean while preserving error visibility.
