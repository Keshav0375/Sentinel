## Plain English Summary

### What problem it solves

Sentinel's agents need tools — callable functions that let them look up service metadata, fetch logs, search past incidents, and so on. But these tools need external resources to do their work: the service database, the past-incident memory store, the current scenario's log data. If we passed those resources as parameters that the LLM must supply, the agent would see them in the tool's input schema and try to fill them in — which makes no sense. The LLM should only see domain inputs like "which service?" or "how far back?", not implementation details like "which database connection?".

The registry pattern solves this by separating *what the tool needs from the LLM* from *what the tool needs from the system*. System dependencies go in at construction time and are hidden from the LLM. Domain inputs appear in the tool's typed signature and are what the LLM provides.

### What was built

**`ToolDeps`** is a simple Python dataclass that bundles everything a tool might need from the system:
- `semantic_memory` — a `SemanticMemory` instance for looking up service ownership and runbooks
- `episodic_memory` — an `EpisodicMemory` instance for searching past incidents by similarity  
- `scenario` — the active scenario file (in the MVP, tools read synthetic logs and deploys from this instead of calling real APIs)

**`build_tools(deps: ToolDeps) -> list[FunctionTool]`** is the factory that creates all 8 tools in one call. Each tool is built using the *closure injection* pattern:

```python
def make_service_lookup_tool(memory: SemanticMemory) -> FunctionTool:
    @function_tool
    async def get_service_metadata(service_name: str) -> str:
        """Get ownership, tier, on-call channel, and dependencies for a service."""
        return await memory.get_service(service_name)
    return get_service_metadata
```

The `memory` object goes into the closure at the time `make_service_lookup_tool` is called. When the LLM calls `get_service_metadata`, it only provides `service_name` — it never sees `memory`. The tool function itself fetches the data internally.

**Scaffolded tool modules** — each of the 7 tool files (`service_lookup.py`, `log_fetcher.py`, etc.) now exports a `make_*` factory function with the correct signature and tool name. They currently raise `NotImplementedError` as placeholder bodies, which tasks 4.2–4.8 replace with real implementations.

**The tool inventory (8 tools total):**
1. `get_service_metadata` — service map lookup (semantic memory)
2. `fetch_logs` — synthetic log retrieval (scenario data)
3. `list_recent_deploys` — deploy history lookup (scenario data)
4. `search_past_incidents` — similarity search (episodic memory)
5. `draft_rollback_pr` — draft a rollback PR artifact (no deps)
6. `draft_hotfix` — draft a hotfix patch artifact (no deps)
7. `draft_slack_summary` — format incident Slack message (no deps)
8. `request_human_approval` — HITL gate that blocks until human responds (no deps)

### Key design decisions

- **`ToolDeps` is a dataclass, not a Pydantic model** — it's an internal DI container, not a domain model crossing API boundaries. No validation needed; dataclass is simpler and less overhead.
- **Agents receive the list, not the registry** — `build_tools(deps)` returns a plain `list[FunctionTool]`. Agents are constructed with `Agent(tools=tools)`. No agent knows about `ToolDeps` or individual tool modules — the coupling is minimal.
- **Lazy imports inside `build_tools`** — each tool module is imported inside the function body at call time. This means importing `registry.py` doesn't eagerly import all tool modules, keeping startup overhead low and circular import risk zero.
- **Stubs raise `NotImplementedError`** — tool stubs that raise are better than returning fake data. The SDK wraps the exception and sends an error back to the LLM, which is at least honest. Fake data could mislead an agent into incorrect reasoning.
- **Tool name comes from the function name** — the `@function_tool` decorator uses the Python function name as the LLM-visible tool name. By naming the inner function `get_service_metadata`, the tool is automatically named that in the LLM's schema. No manual name overrides needed.
