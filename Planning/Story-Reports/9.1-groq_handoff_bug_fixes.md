## Plain English Summary

### The Problem

Sentinel was hard-wired to run on Groq's API, and there were three known issues
that would cause the multi-agent handoff pipeline to fail when you ran it end-to-end:

1. **Wrong API mode.** The OpenAI Agents SDK defaults to using the "responses" API
   endpoint, but Groq only supports the "chat completions" endpoint. Without explicitly
   telling the SDK which mode to use, it would try to call an endpoint that Groq doesn't
   have, causing a network error mid-pipeline.

2. **Strict JSON schema validation errors.** When an agent calls a tool, the SDK
   sends the tool's input schema to the model for validation. With `strict_mode=True`
   (the SDK default), the schema is extra rigid — some fields become required even when
   they have defaults. Groq's models sometimes generate slightly looser JSON that fails
   this strict validation, causing tool calls to be rejected before the tool even runs.
   The fix is to set `strict_mode=False` on every tool decorator so the schema is
   more permissive.

3. **Too-low turn cap.** The `max_turns` setting was set to exactly 15, which is the
   total tool-call budget. But each handoff between agents also counts as a turn in the
   SDK's counter. With 5 specialist agents, the orchestrator can exhaust the budget
   just on handoffs before any real tool work happens. Adding +5 gives the handoffs
   their own headroom without changing the effective tool-call cap.

4. **Ambiguous handoff syntax.** Groq's models sometimes try to pass arguments when
   calling a handoff function (e.g. `transfer_to_triage_agent(incident_id="...")`),
   but handoffs in the OpenAI Agents SDK take no arguments. Adding an explicit rule
   to the orchestrator prompt ("pass no arguments") prevents the model from hallucinating
   an argument that causes a schema mismatch and a failed handoff.

### What Was Done

**SDK init calls** (`set_default_openai_api` + `set_tracing_disabled`) were added to all
three pipeline entry points (the FastAPI app startup, the `run_scenario.py` script, and
the `eval/runner.py` batch runner). These run once at startup, before any agents are built.

**`strict_mode=False`** was added to all 8 `@function_tool` decorators across the 7 tool
files. The plan used the term `strict_json_schema=False`, but the current SDK version
(0.17.0) uses `strict_mode=False` — same concept, different parameter name. This will
be unified under a single parameter name when we upgrade to `openai-agents[litellm]`
in task 9.3.

**`max_turns + 5`** was applied in all three `Runner.run(...)` call sites.

**Orchestrator prompt** got one new bullet under Handoff Rules.

### Key Decision

The plan referenced `strict_json_schema=False`, which doesn't exist in agents 0.17.0.
Rather than add a dummy kwarg that would crash at runtime, the equivalent `strict_mode=False`
was used instead. A note was added to the TODO for 9.1 so this decision is traceable.
When we upgrade to `openai-agents[litellm]` in task 9.3, the parameter naming may change
and this will need a second look.
