## Plain English Summary

### What problem it solves

After the Log Analyst identifies error patterns, the Deploy Correlator agent needs to ask: "Was there a recent deploy that could have caused this?" Asking about deploys in the last 2 hours is the most common way to detect the culprit — a bad commit deployed 15 minutes before an error spike is a strong signal.

`list_recent_deploys` gives the agent a time-filtered view of deploy history for a specific service, formatted as a human-readable summary with all the details needed to assess suspicion: timestamp proximity to the incident, who deployed it, which commit, and how many files changed.

### What was built

**Tool signature** (required parameters only — all are integers or strings, strict mode compatible):

```
list_recent_deploys(
    service_name: str,   # e.g. "api-gateway"
    hours_back: int,     # how far back to look — start with 2, expand if empty
) -> str
```

**How it works step by step:**

1. **Validate inputs** — if `scenario` is None, service is empty, or `hours_back ≤ 0`, return an error string.

2. **Determine reference time** — the key challenge with synthetic data is that scenario timestamps are fixed historical dates (2026-05-10), but `datetime.now()` would be today's date. If we used "now" as the reference for `hours_back`, we'd never find any deploys because they'd all be in the distant past. Instead, `_get_reference_time()` reads the scenario data directly — it takes `max(latest_log_timestamp, latest_deploy_timestamp)` as the "incident time". This gives us the right anchor point for the look-back window.

   For `bad_deploy_01`: the latest log is at `03:00:01Z`, the culprit deploy is at `02:44:50Z`, so reference = `03:00:01Z`.

3. **Compute the window** — `window_start = reference_time - timedelta(hours=hours_back)`. With `hours_back=2`, the window is `[01:00:01Z, 03:00:01Z]`.

4. **Filter deploys** — calls `generate_deploys(scenario)` (already sorted newest-first) and keeps only entries where `service == service_name` AND `timestamp` falls within the window.

5. **Format the results** — returns a block-per-deploy string showing deploy_id, timestamp, author, commit_sha, files_changed, and description. If no deploys found, returns a clear message so the agent knows to expand the window.

Example output for `bad_deploy_01` with `hours_back=2`:
```
Found 1 deploy(s) for 'api-gateway' in the last 2 hour(s) (before 2026-05-10T03:00:01Z):
deploy_id:     deploy-abc123
  timestamp:     2026-05-10T02:44:50Z
  author:        ci-bot
  commit_sha:    a1b2c3d4e5f6
  files_changed: 5
  description:   Add JWT validation to AuthMiddleware
```

### Key design decisions

- **`_get_reference_time()` uses scenario data, not `datetime.now()`** — this is the most important design decision. Synthetic scenario logs and deploys have fixed historical timestamps. Using `datetime.now()` as the reference point would make `hours_back` meaningless. By reading `max(log.ts for log in scenario.logs, deploy.ts for deploy in scenario.deploys)`, the tool correctly anchors the time window to when the incident occurred in the scenario.

- **Direct scenario attribute access for timestamps** — `_get_reference_time` reads `scenario.logs` and `scenario.deploys` directly (Pydantic models with `ts: datetime` fields), rather than calling `generate_logs()` or `generate_deploys()`. This avoids the overhead of generating full `LogEntry`/`Deploy` objects just to find a max timestamp.

- **Service-level filtering** — even when multiple services have deploys in the scenario (distractor deploys), the tool only returns deploys for the requested service. The Deploy Correlator agent should call this once for the affected service; it won't accidentally see other services' deploys.

- **Same testability pattern** — logic extracted to `_list_recent_deploys`, `_get_reference_time`, `_filter_deploys`, and `_format_deploys` so tests call helpers directly without SDK `ToolContext`.

### Test coverage (36 tests)

*Tool wrapping (6):* Returns `FunctionTool`, correct name, non-empty description, schema has `service_name` and `hours_back`, `scenario` not in schema.

*Error handling (5):* None scenario → error string (no raise), empty service name, zero hours_back, negative hours_back.

*Correct filtering (11):* Culprit deploy (`deploy-abc123`) appears with `hours_back=2`, old deploy (`deploy-xyz789`, ~13h before) excluded with `hours_back=2` but included with `hours_back=24`, deploys from other services excluded, user-service deploy found when querying user-service, unknown service → "No deploys found", culprit deploy_id matches scenario `ground_truth.deploy_id`.

*Output content (4):* Contains `Found N`, timestamp, author, commit SHA and files_changed count.

*`_get_reference_time` (3):* Correct date (2026-05-10T03:00:01Z), timezone-aware, after culprit deploy.

*`_filter_deploys` (4):* Service-name filter, excludes pre-window deploys, keeps in-window deploys, empty for unknown service.

*`_format_deploys` (5):* Empty → "No deploys found", header count, deploy_id present, all fields present (timestamp/author/commit/files_changed), multiple deploys both shown.
