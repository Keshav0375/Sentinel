## Plain English Summary

### What Problem This Solves

When an incident pipeline is running, the dashboard (or any connected client) needs two things:
1. **A live feed** of what the agent pipeline is doing — which agent is active, what tool was called, when the HITL gate fires.
2. **A way to approve or reject** the remediation action without typing in a terminal.

Task 6.7 connects these two needs through a pair of HTTP endpoints.

### What the Code Does (Step by Step)

**`GET /events/{incident_id}` — SSE Stream**

When a browser or client connects to this endpoint, the server doesn't respond immediately with a full body. Instead, it opens a persistent connection and streams events as they happen using the [Server-Sent Events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events) protocol. Each event looks like:

```
data: {"type": "agent_started", "agent_name": "triage_agent", ...}\n\n
```

Internally, the endpoint calls `event_bus.subscribe(incident_id)` to get a queue, then loops on `await queue.get()`. Every time the pipeline publishes a new `PipelineEvent`, it lands in the queue and gets serialized and yielded to the client. When the pipeline finishes, `close_incident` puts a `None` sentinel in the queue, which breaks the loop and closes the stream cleanly.

**`POST /incidents/{incident_id}/approve` — HITL Resolution**

When the remediation agent needs human approval (e.g., "roll back this deploy?"), it calls `request_human_approval`, which in dashboard mode:
1. Creates a `HitlGate` (an asyncio.Event) for the incident in `HitlGateRegistry`
2. Publishes a `hitl_requested` event so the dashboard can show an Approve/Reject UI
3. **Blocks** — waits on `await gate.event.wait()`

When the human clicks Approve or Reject in the dashboard, it POSTs to `/incidents/{id}/approve`. The endpoint:
1. Looks up the active gate for that incident
2. Stores the decision ("approve"/"reject") and optional comment
3. Calls `gate.event.set()` — this unblocks the waiting remediation agent

**Incident Context Propagation**

Because the approval function needs to know which incident it's handling (without passing an extra argument through the entire agent call stack), `set_current_incident(incident_id)` stores the ID in an `asyncio.ContextVar` at the start of each pipeline run. The approval function reads it with `_CURRENT_INCIDENT_ID.get()`. `reset_current_incident(token)` restores the previous value in a finally block.

**`make_api_approval_fn` — Wiring It All Together**

This factory function creates the `ApprovalFn` callback that replaces the `input()` terminal handler. It closes over both `event_bus` and `gate_registry`, so when the remediation agent calls `request_human_approval`, the flow is:
- Read current `incident_id` from ContextVar
- Create a HITL gate in the registry
- Publish `hitl_requested` event to the bus
- Await the gate event
- On resolution: publish `hitl_resolved`, clear the gate, return the decision

### Key Decision: Test Fix (The Tricky Part)

The original SSE tests used `threading.Thread` to run `close_incident()` from a separate thread with a new event loop. This should work in theory — but in practice, `asyncio.Queue.put()` from a foreign event loop doesn't reliably wake up `await queue.get()` in the ASGI app's event loop. The `Future.set_result()` call schedules a callback on the ASGI loop via `call_soon()` (not `call_soon_threadsafe()`), so the selector never gets a wake-up signal and the queue getter blocks indefinitely.

**Fix:** Converted all SSE tests from synchronous (using `TestClient` + threads) to fully async (using `httpx.AsyncClient` with `httpx.ASGITransport`). In this mode, the test code, the ASGI app, and the `close_incident()` call all share a single event loop — so queue operations are atomic and reliable. `asyncio.TaskGroup` coordinates the streaming consumer and the delayed close.

```python
async with asyncio.TaskGroup() as tg:
    tg.create_task(_stream_events())      # consumer: reads until stream closes
    tg.create_task(_send_and_close())     # producer: publishes then closes after 50ms
```
